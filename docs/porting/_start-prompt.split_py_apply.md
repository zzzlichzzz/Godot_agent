## §2 Контракт правки

**2.1 Поведение `split_apply` — по эталону, дословно:**

| ситуация | эталон `apply_prepared_split` | требование в порте |
|---|---|---|
| в плане есть `errors` | `SplitError("план не готов к применению: …")` | отказ **до** любой записи, `invalid_input` |
| донор исчез | `StaleSplitError("файл-донор исчез: …")` | `not_found`, ничего не записано |
| `sha256(донор) != donor_sha256` плана | `StaleSplitError("файл-донор изменился после plan_split")` | `stale_plan`, ничего не записано |
| текст модуля не компилируется | `SplitError("<rel>: текст модуля не компилируется")` | отказ до записи |
| целевой файл уже существует | `StaleSplitError("целевой файл уже существует: <rel>")` | `stale_plan` |
| успех | `{donor, written, moved, facade_lines}` | те же поля + квитанции воронки |

Порядок обязателен: **сначала все проверки всех модулей и фасада, потом запись** — частичной
записи «половина модулей создана» быть не может.

**2.2 Воронка получает два новых `op`:**

- `create` — цель **не должна существовать**; `expected_hash=""` означает «файла быть не должно»
  (наличие файла при `create` — `stale_plan`).
- `delete` — цель должна существовать и совпасть по `expected_hash`; шаг несёт `compensates`,
  если удаляет то, что создал план.

`script_edits.apply_step` **обязан** разбирать `op` явно (сейчас он его игнорирует: единственный
путь — правка существующего текста), неизвестный `op` → `AppError("invalid_input")`, не «тихий
replace».

**2.3 ADR-0015 обязан ответить минимум на пять вопросов:**

1. Как «файла быть не должно» кодируется в `expected_hash` и почему это не ломает старые планы
   (`write_preview`, `symbol_rename`) — их пины доказывают обратную совместимость.
2. Что такое компенсация `delete` и в каком порядке откат удаляет созданные файлы (обратный
   порядок шагов; донор восстанавливается из `store/backups.py` **побайтово**).
3. Как это соотносится с ADR-0005: воронка остаётся одной формой `Step/Receipt/WritePlan`,
   `scene_ops` и `project_ops` `create/delete` не получают.
4. Почему создание файла не идёт напрямую из `app.py` мимо WAL (запрещено) и что видит
   recovery `write_apply`, если процесс умер между `create` и правкой донора.
5. Границы PathPolicy: `create`/`delete` уважают те же правила, что `write_preview` (вне
   addon-root нельзя, `plugin.cfg` и каталог `addons/` защищены), удаление каталога запрещено.

**2.4 Архитектура:** IO только в `app.py`/порте, `domain/apply.py` — чистые функции; лимиты файлов
и длины строк соблюдены (`check_limits`), глобальных кэшей нет.

**2.5 Контракт:** новый артефакт `contract/capabilities/split_apply.json`, `gen_contract --check`
**25 → 26**; схема результата строгая — ровно поля из 2.1, без «полезных» добавок.
