# ADR-0004. Владельцы инструментов и вклады в составные инструменты

Статус: принято (2026-10-27). Основание: находки 2, 3, 4 ревью.

## Контекст

Одно имя инструмента обслуживали несколько модулей (`write_preview` —
`editing.write_preview`, `editing.scene_ops`, `editing.resource_ops`,
`editing.file_refactor`; `check` — четыре проверки). Это были комментарии в
шапках, а не работающая модель: автозагрузчик получил бы либо конфликт имён,
либо несколько реализаций одного инструмента.

Отдельно: агрегатор `check` был спрятан в `protocol/` только потому, что
модулю запрещено звать модуль. Выбор проверок, порядок, частичные ошибки и
склейка результата — прикладная логика, ей не место в протоколе.

## Решение

Манифест модуля объявляет **четыре разных вида** отношений с реестром:

| Поле | Смысл | Ограничение |
|---|---|---|
| `provides_tools` | публичные имена, у которых модуль — **владелец** | имя принадлежит ровно одному модулю |
| `contributes_to` | вклад в **чужой** составной инструмент | вклад не публикует имя, только реализует интерфейс вклада |
| `internal_services` | возможности без публичного имени (HTTP-маршрут, кнопка панели) | канал не импортирует модуль, он подключается по манифесту |
| `requires` | зависимость от **публичного API** другого модуля | только `__init__.py` модуля, не `domain/`, не `app.py` |

Владелец составного инструмента вызывает вклады **через реестр**, а не
импортом: `ctx.registry.contributions("check")`.

### Кто чем владеет

| Инструмент | Владелец | Вклады |
|---|---|---|
| `check` | `verification.check` | `gd_lint`, `tscn_lint`, `api_check`, `headless` |
| `write_preview` / `write_apply` / `write_rollback` | `editing.write_preview` / `write_apply` / `rollback` | `scene_ops`, `resource_ops`, `file_refactor`, `symbol_rename` — компиляторы операций |
| `usages` | `code_intel.usages` | `symbol_rename` (проверка доказательства ссылок) |
| `scene` | `scene_model.tree` | `connections`, `scene_deps`, `node_info` |
| `context` | `context.gather` | `editor_context`, `runtime_snapshot`, `architecture` |
| `paths_preview` | `editing.paths_preview` | `file_refactor` (расчёт ссылок) |

`check` переехал из `protocol/` в `modules/verification/check/`.
`protocol/` теперь только валидирует, вызывает и сериализует — композиции там нет.

### Тип вклада

Интерфейсы вкладов — данные, а не код конкретной фичи:

- `verification/shared/check_contract.py` — `CheckContribution` (имя, что
  проверяет, `run(target) -> findings[]`, `kinds`);
- `context/shared/context_section.py` — `ContextSection` (имя, стоимость,
  `collect(target) -> fragment`);
- `editing/shared/operation_compiler.py` — `OperationCompiler` (`op` → шаг плана).

## Правила, которые из этого следуют

1. Два `provides_tools` с одним именем → **оба** кандидата в `disabled` с
   причиной `conflict`, а не «кто последний загрузился». Иначе поведение зависит
   от порядка обхода папок.
2. `contributes_to` на несуществующий инструмент → модуль грузится, но вклад
   игнорируется с предупреждением в health: вклад — не критичная зависимость.
3. `requires` на отсутствующий/отключённый модуль → зависимый модуль
   отключается **транзитивно** (R-03), а не падает при первом вызове.
4. Публичное API модуля — только то, что реэкспортировано в `__init__.py`.
   Импорт `modules.<область>.<фича>.domain.*` другим модулем — нарушение.

## Следствия

- Конфликт имён перестаёт быть «повезёт/не повезёт»: он виден в health на старте.
- `protocol/` худеет; агрегаторы живут рядом с проверками, которые агрегируют.
- Удаление модуля-вклада не ломает владельца: вклад просто исчезает из списка.
