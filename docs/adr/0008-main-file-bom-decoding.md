# ADR-0008: UTF-8 BOM только на границе основного файла проверки

**Дата:** 2026-10-31. **Статус:** решение согласовано пользователем для F1;
реализация сдаётся отдельным срезом C.10, приёмка аудитора ещё не выполнена.

## Контекст

Аудит C.9 нашёл унаследованный C.2 false-clean: BOM-only `.gd` считался чистым,
а `var`/`func` первой строки с BOM не попадали в regex-проверки. Корпус C.2
018/019/035 пинил чистый `lint_gdscript` на utf-8-тексте, но основной файл
эталон `project_tools.read_project_file` читает utf-8-sig/errors=replace.

Три actual-old повторных вызова `_check_one_path` и24 новых файловых кейса
подтвердили правильную границу. Старые raw-text наблюдения не удаляются:
они остаются в `reference_text_messages`/`previous_expect` и отдельном тесте.

## Решение

Общий чистый `verification/shared/source_text.py:decode_source` декодирует
исходные bytes через incremental utf-8-sig/errors=replace, final=True,
без newline-normalization. Именно потоковый decoder эталонного TextIOWrapper,
а не bytes.decode: для неполного BOM-префикса EF BB старый файл даёт пустой
текст, тогда как bytes.decode даёт U+FFFD. Это наблюдение запинено кейсом046;
мы не «исправляем» дополнительную старую особенность при ремонте F1.
Его вызывают `gd_lint.domain.core.check(raw)` и `verification.check.app`.
Снимается ровно один ведущий UTF-8 BOM; повторный/внутренний U+FEFF сохраняется.
Лимит и `checked_bytes` считают исходные байты до декодирования.

Публичный `lint_gdscript(text)`, его алгоритм/порядок/сообщения не меняются.
Стандартный `utf-8-sig` выполняет конверсию данных, не IO. Зависимости остаются
в пределах verification/shared; новых инструментов/портов/контрактов нет.

## Границы

- `check(path, content)` принимает уже заданный candidate; BOM не снимается.
- Эталон `tscn_lint._scene_node_paths` читает instance через utf-8, не sig;
  принятые `tscn_lint` app/domain/read_inputs и65корпусных кейсов не меняются.
- Общий DiskFS не меняется: read_raw по-прежнему отдаёт точные исходные bytes.
- CRLF/lone-CR, маскирование, PathPolicy, ошибки и4МиБ-квота не меняются.
- Не закрываются прежние wiring/i18n/CLI/headless долги и blind spot C.9 №006.

## Альтернатива и доказательства

Просто принять BOM-границу означало бы оставить false-clean; пользователь
выбрал её ремонт. Глобальное stripping либо правка чистого сканера изменили бы
candidate/внутренний U+FEFF и другие принятые consumers — отвергнуто.

Дельта разрешает только общий декодер, две файловые точки входа, три ожидания
C.2 с сохранением старых oracle-данных, дополнительный C.9 корпус, связанные
тесты/документы. Снятие decoder, замена только одного consumer и over-strip
обязаны краснить свои тесты; submitted-byte backup/SHA/EOL после каждой мутации.
Карточки, принятое tscn-ядро и форматный слой доказываются byte-identical.
