# ADR-0014. Второй узкий потребитель fs.exists: read-only split_plan

Статус: разрешено пользователем для C.18 (2026-11-01, §10/B4).

## Решение

К существующему вызову `editing.split_gd/plan_io.py` из ADR-0011 добавляется
ровно один production-вызов `fs.exists` в `editing.split_py/app.py`. Он читает
только метаданные целевых `.py` модулей плана внутри проверенного аддона.
Файл и каталог одинаково считаются занятой целью. Consumer-owned FileSystem
добавляет метод exists; substrate и прежний `.gd` потребитель не меняются.
Это не разрешение общего metadata-сервиса или доступа вне PathPolicy.

## Уточнение формы ответа

После двух живых вызовов на каждой фикстуре пользователь явно выбрал
«Паритет эталона»: занятая цель добавляет `целевой файл уже существует: <rel>`
в `errors` полного плана с `ok:true`, а не вызывает AppError. Противоречащее
требование исключения в §10/B4 отменено этим уточнением; прочие пункты сохранены.
Так делает native `split_refactor.py:573–574`, без записи на диск.

## Проверки

Корпус077/078 содержит actual-native результат для файла/каталога, повторный
ответ и неизменность дерева. Новый тест закрепляет ровно два production-вызова
`fs.exists` и точные пути обоих потребителей. Мутация exists→is_file должна
покраснить каталог, не меняя accepted `.gd` код/адаптер.
