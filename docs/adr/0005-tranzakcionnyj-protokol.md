# ADR-0005. Транзакционный протокол записи

Статус: принято (2026-10-27). Основание: находка 5 ревью — атомарность обещана,
модель не описана.

## Контекст

`atomic_write` (temp + rename) защищает **один** файл. План может менять
несколько файлов, открытую в редакторе сцену и `project.godot` — и это уже не
атомарно. Не были описаны: журнал до первого эффекта, восстановление после
падения, версия редактора в stale-check, блокировка интервала «проверил →
применил», идемпотентный повтор, и защита отката от затирания чужой правки.

## Решение

### Состояния плана (durable)

```
DRAFT ──prepare──► PREPARED ──apply──► APPLYING ──ok──► COMMITTED
                       │                   │
                       │                   └─сбой──► ROLLING_BACK ──► ROLLED_BACK
                       └─истёк TTL/отмена──────────► EXPIRED
```

- **PREPARED** — план, диффы, `expected` (хеши файлов + `editor_revision`
  открытых сцен) и `digest` уже записаны в WAL

**Что именно хешируется (`expected`).** Это контракт, а не деталь реализации —
уточнён аудитом среза `write_preview` (2026-10-27), потому что от него зависит,
сравнит ли часть 2 одинаковые вещи:

- `expected[path]` — sha256 **сырых байтов** файла (включая BOM и переводы
  строк): побайтовый stale-check, любое внешнее изменение — расхождение;
- `steps[].expected_hash` — sha256 **нормализованного** текста (`\r\n`, `\r` →
  `\n`, BOM снят): это текст, **в котором посчитаны смещения** правок, и по нему
  проверяется, что правки ещё применимы;
- `payload.newline` — `"crlf"` или `"lf"`, определяется по **байтам**
  (`b"\r\n" in raw`), а не по тексту: текстовое чтение через universal newlines
  эту разницу скрывает (так `newline` всегда получался `"lf"`).

Часть 2 обязана: читать `read_raw`, сверять `expected[path]` с байтами,
применять правки к нормализованному тексту и **восстанавливать исходный стиль**
файла (`payload.newline`) — иначе CRLF-скрипт превратится в LF и в диффе будет
весь файл.
  (`user://godot_agent/journal/<plan_id>.jsonl`) и сброшены на диск (`fsync`).
  Пока WAL не записан, побочных эффектов нет вообще.
- **APPLYING** — по каждому шагу пишется **квитанция**: `step_id`, `op`,
  `applied_hash`, `undo_token` (для редактора — id undo-скоупа). Квитанция
  пишется **после** эффекта и **до** следующего шага.
- **COMMITTED** — все квитанции на месте. `entry_id` для `rollback` — это
  `plan_id` + номер записи журнала.
- **ROLLING_BACK** — обратный проход по квитанциям, от последней к первой.

### Recovery при старте

`runtime/bootstrap.py` на старте читает WAL:

| Найдено | Действие |
|---|---|
| `PREPARED`, эффектов нет | план помечается `EXPIRED`, ничего не трогаем |
| `APPLYING` с квитанциями | автоматический откат по квитанциям → `ROLLED_BACK`, отчёт в лог и `health` |
| `APPLYING` без квитанций | `PREPARED`-случай (эффекта не было) |
| `COMMITTED` | ничего: это история для `rollback` пользователя |

### Stale-check и блокировка

`apply` под per-project мьютексом (файл-лок в `user://godot_agent/lock`) в
одном неделимом интервале:

1. перечитать `expected` (хеши файлов, `editor_revision`, `dirty` открытых сцен);
2. сравнить с тем, что записано в PREPARED → расхождение = `stale_plan`;
3. применить шаги, писать квитанции;
4. снять лок.

Проверка «до» и применение не разделяются другим процессом: лок держится весь
интервал.

### Идемпотентность

- `apply(plan_id)` с `digest`, равным сохранённому, и найденным `COMMITTED`
  → возвращается **та же квитанция** (`entry_id`), без повторного эффекта.
- `apply(plan_id)` с другим `digest` → `stale_plan`.
- Повторный `rollback(entry_id)` → `conflict` с `details.state = "already_rolled_back"`.

### Подтверждение пользователя

Кнопка «применить» в панели привязана к `digest` плана и имеет TTL (по
умолчанию 15 минут). Подтверждение, выданное для одного digest, не применяет
другой план: подмена содержимого между показом и нажатием — это `stale_plan`,
а не «печаль».

### Редакторская половина

Правка открытой сцены идёт батчем, а не серией одиночных вызовов:

```
editor_apply_batch(plan_id, digest, expected_revision, steps[]) -> receipts[]
```

- `expected_revision` — версия открытой сцены; несовпадение → `stale_plan`;
- батч выполняется в одном undo-скоупе: пользователь отменяет правку одним
  Ctrl+Z, а не десятью;
- потеря ответа редактора не считается успехом: `apply` переспрашивает
  состояние и вставляет отсутствующие квитанции только если `applied_hash`
  совпал (идемпотентность на стороне редактора).

### Откат и чужая правка

`rollback` перед восстановлением сверяет `post_hash` файла с
`applied_hash` из квитанции:

- совпало → восстанавливаем байт-в-байт;
- не совпало (файл изменили после `apply`) → `conflict` с путём и хешами,
  восстановление **не выполняется**. Затереть чужую работу хуже, чем не откатить.

## Инварианты отчёта и идентификаторов

- **`step_id` = `res://`‑путь файла.** В этом контракте один шаг на файл, поэтому
  `step_id` совпадает с `target`; квитанции и `rollback` адресуются им. Если
  появится второй вид операции на тот же файл (часть B/C), формат станет
  `<target>#<k>` — это ломающее изменение WAL, и оно делается отдельной
  миграцией, а не «по ходу».
- **Причины `conflict` — закрытый набор** (`editing/shared/conflict_reasons.py`):
  `unverified_references`, `dynamic_references`, `all_usages_excluded`,
  `name_conflict`, `already_applied`, `already_rolled_back`, `lock_busy`,
  `no_receipts`, `backup_missing`, `backup_mismatch`, `post_state_mismatch` и
  параметрическая `plan_state:<STATE>`. Новая причина добавляется в набор,
  в этот раздел и в контрактный тест — иначе она появляется молча.
- **`conflict` обязан иметь `hint`:** клиент должен понимать следующий шаг
  (`already_rolled_back` → «сделай новый `write_preview`»).

## Тесты, без которых это не считается сделанным

| Сценарий | Ожидание |
|---|---|
| сбой между шагами 2 и 3 | откат шагов 1–2, проект в исходном состоянии |
| `kill` процесса в `APPLYING` | recovery при старте откатывает по квитанциям |
| повторный `apply` с тем же digest | та же квитанция, эффекта нет |
| файл изменён после `apply` | `rollback` → `conflict`, файл не тронут |
| две сессии одновременно | второй получает `conflict` по локу, а не портит план |
| сцена изменена пользователем между preview и apply | `stale_plan` |

Прогон — на **реальной** временной копии проекта (NTFS), а не только на
`MemoryFS`: rename-семантика и локи в памяти ведут себя иначе.
