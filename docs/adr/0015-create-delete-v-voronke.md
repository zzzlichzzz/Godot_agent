# ADR-0015. Create/delete внутри единой воронки записи

Статус: принято аудитором 2026-11-01 (сессия 76) — C.20 принят, замечания F1–F3 (запись, не код) — в листе механики.

## Контекст

Принятая воронка ADR-0005 меняет только существующий текст: каждый target
читается и получает сырой backup. `split_apply` должен атомарно создать новые
`.py`-модули и заменить донора фасадом. Прямая запись из механики нарушила бы
R-12, а обычный overwrite не отличает «создать отсутствующий файл» от
«затереть появившуюся после preview цель».

## Решение

### Отсутствие как expected

Для file-step `op="create"` значение `expected_hash=""` означает ровно
«target отсутствует». Проверка выполняется под тем же project lock до эффекта;
существующий файл **или каталог** даёт `stale_plan`. Пустая строка допустима
только для `create`: прежние `script_edit`-планы `write_preview` и
`symbol_rename` продолжают требовать непустые хеши и не меняют форму.

`delete` требует существующий обычный файл и точный sha256 сырых байтов в
`expected_hash`; каталог удалять нельзя. Неизвестный `op` — `invalid_input`,
а не неявный `script_edit`.

### Компенсации и порядок

Create-шаг несёт `compensates="delete"`. Его receipt фиксирует sha256
созданных байтов и пустой backup-token. При rollback/recovery post-state
сначала сверяется с receipt; затем созданный файл удаляется. Квитанции идут в
обратном порядке: сначала donor восстанавливается из `store/backups.py`
побайтово, затем созданные модули удаляются от последнего к первому.

Обычный forward `delete` сохраняет удаляемые сырые байты в backup и при
компенсации восстанавливает их. Это другая ситуация, чем compensation-delete
для create: первая имеет backup, вторая доказывает отсутствие через
`expected_hash=""`.

### Совместимость с ADR-0005

Форма остаётся единственной: `Step` → `WritePlan` → durable WAL → `Receipt`.
Новых протоколов и прямой записи нет. `scene_ops` и `project_ops` не получают
file-операции `create/delete`; расширяется только исполнитель файловых шагов.
Принятые `write_preview`, `write_apply`, `write_rollback` и `symbol_rename`
сохраняют прежние планы и проверяются без изменения их старых тестов.

`split_apply` сначала валидирует все module/facade-тексты и свежесть всех
targets, затем пишет `PREPARED`, берёт project lock через общий apply и только
после `APPLYING` создаёт первый файл. Receipt каждого эффекта durable до
следующего шага; `COMMITTED` появляется последним.

Если процесс умер между завершённым create-шагом и правкой donor, recovery
видит `APPLYING` и receipt созданного target, переходит в `ROLLING_BACK` и
удаляет файл через его `compensates="delete"`. Если ни одной квитанции нет,
эффект не доказан и действует прежнее правило ADR-0005 `left_prepared`.

### PathPolicy

Каждый target до IO проходит тот же `funnel.guard_path`, что `write_apply`:
выход из project root, запрещённый addon-root, `plugin.cfg` и защищённый
каталог `addons/` отклоняются. Адаптер повторно проверяет containment и не
следует наружу через realpath. `create` не перезаписывает существующее,
`delete` не удаляет каталог.

## Последствия

- Split-механика передаёт только данные шагов; проект пишет общий apply.
- Сбой после любого подтверждённого шага восстанавливается в обратном порядке.
- Пустой expected становится типизированным sentinel только для create, а не
  общим ослаблением stale-check.
- Нужны disk/memory-пины, интеграция на реальной временной копии, recovery,
  отказ каталога и побайтовый `apply + rollback`.

## Проверки

- `tests/py/security/test_split_apply_write.py`: ни одной записи из
  `split_py`, PathPolicy и WAL до эффекта.
- C.20 unit/integration: occupied create, exact-hash delete, delete-каталог,
  сбой второго шага, recovery, обратный порядок и byte-exact rollback.
- Старые тесты `write_preview`/`write_apply`/`write_rollback` проходят без
  ослабления или переписывания.
