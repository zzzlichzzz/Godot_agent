# ADR-0003. Композиция: кто кого вызывает и как модуль получает реализацию

Статус: принято (2026-10-27). Основание: находка 1 ревью — направление описано,
связывание нет.

## Контекст

Правила говорили «порт объявляет потребитель, реализует `substrate`», но не
говорили, **как** реализация попадает в модуль. Два варианта одинаково
«соответствуют правилам», и один из них ломает главное обещание:

- адаптер импортирует `modules/<область>/<фича>/ports.py` — удаление папки
  модуля ломает `substrate`, то есть нарушает R-03;
- `substrate` не импортирует модули вообще — тогда нужно явное место, где
  абстракция и реализация встречаются.

## Решение

**Composition root — `python/runtime/bootstrap.py`. Единственное место, которое
знает и модули, и адаптеры.**

1. `bootstrap` создаёт адаптеры (`DiskFileSystem`, `EditorClient`,
   `HeadlessRunner`, `JournalStore`, `Clock`) и кладёт их в **реестр портов**:
   строковый ключ (`"fs"`, `"editor"`, `"engine"`, `"store"`, `"clock"`) →
   объект реализации.
2. Модуль объявляет в манифесте `requires_ports=["fs"]` и получает в `setup(ctx)`
   узкий **`ModuleContext`**:
   `ctx.profile`, `ctx.settings` (секция своего `id`), `ctx.logger`, `ctx.ids`,
   `ctx.clock`, `ctx.path_policy` (единая политика путей, R-13: что можно читать
   и писать), `ctx.port("fs")`, `ctx.registry` (только чтение вкладов),
   `ctx.call_tool` (для агрегаторов).

Поверхность контекста — **закрытый список**: новое поле появляется правкой этого
ADR, а не по желанию модуля. 2026-10-27: `ctx.path_policy` добавлен при переносе
`project_text.search` — без него модуль не может применить политику доступа, а
дублировать её внутри модуля запрещено (R-13 требует одно место).
3. `ctx.port("fs")` возвращает объект, который **структурно** совпадает с
   протоколом из `ports.py` этого модуля. Импорта между ними нет: `substrate`
   не знает про `modules`, модуль не знает про классы адаптеров.
4. Соответствие проверяется тестом контракта: `typing.Protocol` помечен
   `@runtime_checkable`, `tests/py/contract/` проверяет `isinstance(adapter, Port)`
   для каждой пары «порт модуля — адаптер» из манифеста.

### Lifetime

| Что | Время жизни | Почему |
|---|---|---|
| `fs`, `engine`, `clock` | один на профиль (процесс) | нет состояния, дешёвые |
| `editor` (клиент сокета) | один на профиль | один сокет, одна очередь |
| `store` (журнал, планы, кеш API) | один на проект | привязан к `user://godot_agent/` |
| тестовые двойники (`MemoryFS`, `FakeEditor`) | один на тест | подменяются профилем `test` |

Профиль (`editor` / `headless` / `test`) — единственный переключатель: он
выбирает набор адаптеров. Модуль про профиль не спрашивает, он объявляет
`environment` и `requires_ports`.

## Следствия

- `substrate` не растёт импортами из `modules` — линтер это проверяет.
- Модуль можно удалить, оставив адаптер: адаптер про него не знает.
- Тесты модуля идут на `MemoryFS` без Godot и без реального диска.
- Модуль не создаёт адаптеры сам и не хранит их в глобальных переменных.
- В `ports.py` нет логики: только сигнатуры и типы возврата.

## Альтернативы

- **Глобальный `python/ports/`** — все объявления в одном месте: свалка,
  чужие протоколы под рукой, модуль перестаёт быть самодостаточным.
- **Сервис-локатор по строке без объявления порта** — нет проверки типов, тест
  контракта невозможен.
- **Импорт `ports.py` из адаптера** — нарушает R-03 (удаление модуля ломает
  платформу).
