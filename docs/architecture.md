# Архитектура

Документ отвечает на вопросы «из чего состоит агент», «куда класть новый код» и
«почему именно так». Правила, на которые он опирается, — в `../RULES.md`.

## 1. Три оси, которые нельзя смешивать

Любая путаница в архитектуре начинается с того, что смешивают три разных вопроса:

| Ось | Вопрос | Примеры |
|---|---|---|
| Канал | **как** вызвали | MCP-сервер, HTTP для панели, CLI, панель в редакторе |
| Возможность | **что** делаем | `read`, `search`, `functions`, `write_apply`, `gd_lint` |
| Исполнитель | **кто** физически делает | Python-домен, мост к редактору, headless Godot |

Нейросеть — не слой и не исполнитель. Это **клиент**, такой же как панель или
CLI: она присылает имя инструмента и аргументы. Поэтому «ветка API», «ветка
браузера», «ветка MCP» и «ветка редактора» из старого агента в новой
архитектуре — это не четыре реализации, а один домен и четыре транспорта
(R-04). Ветка имеет право только переводить протокол: разобрать запрос,
вызвать, оформить ответ.

## 2. Слои и правило зависимостей

```
channels/        mcp | http | cli        перевод протокола, ничего больше
    │
protocol/        реестр, схемы, валидация, вызов, маппинг ошибок
    │
modules/         <область>/<фича>/        домен: чистая логика
    │  ↘ shared/  общий код внутри области (не между областями)
    │  ↘ ports.py что нужно домену от мира (typing.Protocol, без реализации)
    ▼
formats/         разбор .gd и .tscn: без IO, без Godot, без знаний о фичах
    ▼
kernel/          универсальные типы: ошибки, пути, diff, ToolSpec, WritePlan, лимиты
    ▲
substrate/       адаптеры: fs, editor, engine, store, llm — реализуют ports.py структурно
    ▲
runtime/         bootstrap.py — композиция: единственное место, знающее и модули, и адаптеры
```

Стрелка — направление знания. Разрешено знать только вниз. Следствия:

- `kernel` знает только стандартную библиотеку и ничего про Godot;
- модуль импортирует `shared` своей области, `formats`, `kernel` и **публичное
  API** другого модуля (`__init__.py`, если объявлено в `requires`); чужой
  `domain/`, `substrate`, `protocol`, `channels` — нельзя;
- порт объявляет потребитель (`ports.py` внутри модуля), реализует `substrate`
  структурно: адаптер не импортирует модуль, модуль не импортирует адаптер, а
  связывает их `runtime/bootstrap.py` (ADR-0003). Глобальной папки
  `python/ports/` нет — объявление живёт рядом с потребителем;
- каналы не лезут в `substrate` напрямую — иначе появится вторая логика;
- `editor/` (GDScript) вообще не знает про домен: он выполняет примитивы.

Если для новой фичи не хватает данных от редактора — расширяется список
примитивов (`contract/editor_verbs.json`), а не добавляется «умная» логика в
GDScript.

## 3. Единица архитектуры — возможность, а не функция

Возможность описывается дескриптором `ToolSpec` (`python/kernel/tool_spec.py`):

| Поле | Зачем |
|---|---|
| `name` | имя инструмента в протоколе (`read`, `write_apply`) |
| `description` | текст для клиента-нейросети: когда применять |
| `args` / `result` | JSON-схемы (источник правды — `contract/`) |
| `effects` | `read` \| `write` \| `exec` — влияет на политику и подтверждения |
| `idempotent` | можно ли повторять без побочных эффектов |
| `preview_of` / `apply_of` | связка «предпросмотр ↔ применение» |
| `errors` | какие `kind` возможны (R-15) |
| `cost` | дешёвая / тяжёлая (сеть, движок, диск) |
| `availability` | профили и `environment` (editor / headless / test) |
| `limits` | лимиты вывода, чтобы ответ не разорвал контекст клиента |

Дескриптор — это **данные**, поэтому их можно проверить линтером, сгенерировать
из них JSON-схемы для всех каналов и сравнить с контрактом.

## 4. Путь одного вызова (чтение)

```
1. канал          MCP пришёл: {"name": "read", "args": {"path": "res://x.gd"}}
2. protocol       находит ToolSpec в реестре, валидирует аргументы по схеме
3. protocol       строит контекст вызова: профиль, политика путей, лимиты
4. модуль         project_text.read: домен решает, что читать и как обрезать
5. порт           FileSystem.read_text(path) — объявление
6. substrate      disk_fs читает файл, проверяет кодировку, следит за лимитом
7. модуль         собирает результат: текст + метаданные (строки, хеш)
8. protocol       оборачивает в форму ответа, ошибки → kind
9. канал          отдаёт клиенту
```

Ни на одном шаге нет «если канал MCP, то…». Канал входит один раз и выходит
один раз.

## 5. Путь записи: одна воронка (R-12, ADR-0005)

```
validate → prepare(PREPARED, WAL+digest) → preview(plan_id)
         → apply(лок: сверка → шаги + квитанции) → COMMITTED → rollback(квитанции)
```

- **plan** — список операций (`write_file`, `replace_range`, `tscn_node_rename`,
  …) плюс диффы, хеши затронутых файлов и `editor_revision` открытых сцен.
- **prepare** пишет план, `digest` и `expected` в WAL
  (`user://godot_agent/journal/<plan_id>.jsonl`) и сбрасывает на диск. До этого
  момента побочных эффектов нет.
- **preview** ничего не меняет: возвращает диффы и `plan_id`; кнопка «применить»
  в панели привязана к `digest` и имеет TTL.
- **apply** держит per-project лок весь интервал «перечитать → сверить →
  применить»: файлы, открытая сцена и `project.godot` проверяются и меняются в
  одном неделимом окне. Расхождение → `stale_plan`. Каждый шаг оставляет
  квитанцию (`applied_hash`, `undo_token`).
- **recovery** при старте: `PREPARED` без квитанций → `EXPIRED`; `APPLYING` с
  квитанциями → автоматический откат; `COMMITTED` → история для пользователя.
- **rollback** сверяет `post_hash` с квитанцией: файл изменили после `apply` →
  `conflict`, восстановление не выполняется. Затереть чужую работу хуже, чем не
  откатить.
- Повторный `apply` с тем же `digest` возвращает ту же квитанцию, а не применяет
  план второй раз.
- Правка **открытой в редакторе** сцены идёт батчем в одном undo-скоупе через
  примитив (`editor/bridge/verbs/guard/mutation_gate.gd`), с `plan_id`,
  `expected_revision` и идемпотентной квитанцией.

Прямая запись файла где угодно, кроме `apply`, — дефект. Это ловится линтером и
тестами ADR-0005 на реальной временной копии проекта.

## 6. Два процесса: GDScript и Python

Godot не исполняет Python. Значит, всегда два процесса:

```
Godot (редактор)                      Python (агент)
editor/                               python/
  bridge/server/socket_server.gd  ←→   substrate/editor/client.py
  bridge/dispatch/dispatcher.gd         (сессия, фрейминг, ретраи)
  bridge/verbs/*                        protocol/dispatch.py
  ui/                                    modules/**
```

Разделение обязанностей жёсткое:

| Сторона | Делает | Не делает |
|---|---|---|
| GDScript | открывает сокет, держит сессию, выполняет примитивы в главном потоке, рисует UI, хранит настройки | не разбирает `.gd`/`.tscn`, не линтит, не считает диффы, не планирует правки, не пишет файлы напрямую |
| Python | домен, анализ, планы, диффы, политика путей, линт, ошибки | не трогает узлы сцены напрямую — только через примитивы |

Примитив — это одно действие, один результат, без ветвления по бизнес-логике:
`scene_open_nodes`, `node_rename`, `node_reparent`, `node_delete`,
`scene_set_property`, `script_apply_edit`, `filesystem_scan`, `settings_get`,
`settings_set`, `editor_selection_get`, `editor_goto_line`, `ui_show_diff`,
`ui_show_plan`, `ui_ask_confirm`, `runtime_run`. Полный список — в
`contract/editor_verbs.json`.

Главный поток: примитивы редактора всегда исполняются в главном потоке
(`bridge/dispatch/main_thread_queue.gd`). Долгие операции (индекс проекта,
headless-прогон, линт) — в Python, чтобы не морозить редактор.

## 7. Модуль: что это и как живёт

Модуль = одна возможность = одна папка:

```
modules/<область>/<фича>/
├─ __init__.py       публичный фасад папки
├─ module.py         манифест ModuleSpec + setup/teardown (≤150 строк)
├─ tools.py          дескрипторы ToolSpec, без логики (≤150 строк)
├─ app.py            сценарий: собрать домен + порты и отдать инструмент (≤ 80 строк)
├─ ports.py          что фиче нужно от мира (typing.Protocol); без реализации
├─ domain/           чистая логика, без IO
├─ settings.py       схема настроек фичи (если нужны)
└─ tests/            тесты этой фичи
```

**Модуль может владеть несколькими инструментами.** `provides_tools` — список:
`code_intel.usages` отдаёт и `usages`, и `analyze_rename`. Это не дублирование, а
два отчёта над одним поиском (R-04): предпросмотр обязан звать существующую
функцию домена, а не делать второй обход проекта. Признак нарушения простой —
объём среза, который «должен быть обёрткой», вырос в разы.

**Граница «предпросмотр ↔ запись».** Предпросмотр показывает, что изменится, и
что не изменится; он **не решает**, применять ли недоказанную ссылку. По эталону
`mode` и `allow_unverified` влияют на исход только в фазе записи
(`symbol_refactor_part3.py:477–498`: `strict` отменяет переименование при
недоказанной ссылке), а в `analyze_rename` они лишь возвращаются в отчёте.
Отсюда правило: параметр, который выглядит как решение, проверяется на эталоне —
если он ни на что не влияет до записи, он не получает поведения «для симметрии».

Манифест (`R-05`): `id` = `область.фича`, `version` (semver), `kernel_api`,
`godot`, `environment` (`editor` / `headless` / `*`), `entrypoints`, `depends` /
`recommends` / `suggests` / `conflicts`, `capabilities`, `settings_schema`,
`health`, `teardown`.

Жизненный цикл: сканирование папок → проверка манифестов (дубли имён
`provides_tools`, неизвестный `contributes_to`, циклы по `requires`) →
топологическая сортировка → `setup` в порядке зависимостей → проверка `health` →
работа → `teardown` в **обратном** порядке.

Правила отказа:

- падение `setup` не роняет агент: частично созданные ресурсы откатываются самим
  модулем (`setup` обязан быть парным к `teardown`), модуль → `disabled` с
  причиной, его инструменты исчезают из реестра;
- зависимые модули (по `requires`) отключаются **транзитивно** с причиной
  `dependency_unavailable`, а не падают при вызове;
- упавший `health` при живой работе → модуль переходит в `degraded`, инструменты
  отвечают `unavailable`, а не молча врут;
- у `setup`/`health` есть таймаут профиля; вызов, прерванный отменой клиента,
  получает `conflict` (`details.reason = cancelled`), а не «завис»;
- повторная инициализация после отключения — через перезапуск профиля, а не
  повторный `setup` на живом модуле.

`environment` — как в платформе модов: модуль, которому нужен живой редактор,
объявляет `editor` и в headless-профиле просто не загружается, а не падает
внутри.

## 8. Ошибки — часть контракта

Ошибка (R-15) — это данные, а не строка:

```
kind      одно из contract/errors.json
message   короткое человеческое объяснение
hint      что сделать дальше (необязательно)
details   структурные данные: path, plan_id, ожидаемое/полученное
```

Базовый набор `kind`: `invalid_input`, `not_found`, `denied`, `stale_plan`,
`conflict`, `engine_down`, `unavailable`, `internal`, `unknown_tool`.

`unavailable` и `unknown_tool` различаются намеренно: первое — «имя известно,
владелец недоступен, можно повторить позже» (модуль отключён, редактор не
поднялся, движок занят), второе — «такого инструмента нет» (опечатка в вызове,
версия клиента новее агента). Реестр помнит имена из `contract/`, поэтому
удалённый модуль отвечает `unavailable` с причиной.

Классификация — в одном месте (`protocol/error_map.py`). Клиент по `kind`
решает, повторять ли вызов, просить ли у человека подтверждение, показывать ли
диалог. Стектрейсы и абсолютные пути наружу не уходят: они в лог.

## 9. Где живёт состояние

Одна из самых частых причин «не поддерживается» — состояние, размазанное по
нескольким местам. Договор:

| Состояние | Владелец | Где лежит |
|---|---|---|
| Файлы проекта | диск | сам проект (`res://`) |
| Планы записи | `substrate/store/plan_store.py` | память процесса + журнал |
| Журнал записей (undo) | `substrate/store/journal.py` | `user://godot_agent/journal/` |
| Кэш Godot API | `substrate/store/api_cache_store.py` | `user://godot_agent/api_cache/` |
| Настройки плагина | `editor/settings/plugin_settings.gd` | `user://` (EditorSettings) |
| Настройки фич | `runtime/config.py` + `settings_schema` модуля | тот же файл настроек |
| Открытые сцены, выделение | редактор Godot | не копируется в Python |
| История диалога | `modules/assistant/history` | `user://godot_agent/history/` |
| Секреты (ключи API) | `substrate/llm/secrets.py` | только `user://`, не в репозиторий |

Правило: у каждого состояния **один** владелец. Если значение нужно в двух
слоях — оно передаётся аргументом, а не читается из глобального места.

## 10. Тесты и лимиты

Пирамида:

| Уровень | Что проверяет | Где |
|---|---|---|
| unit | домен без IO, чистые функции | `modules/<область>/<фича>/tests/` |
| contract | схемы, дескрипторы, `kind` ошибок | `tests/py/contract/` |
| integration | модуль + поддельные порты (память вместо диска) | `tests/py/integration/` |
| e2e | живой Godot headless + настоящий мост | `tests/py/e2e/` |
| parity | сравнение со старым агентом на корпусе входов | `tests/py/snapshots/`, `fixtures/corpus/` |

Лимиты размеров (R-06): файл ≤ 400 строк, `module.py` / `tools.py` ≤ 150,
`app.py` ≤ 80 (только оркестрация), модуль ≤ 3000, область ≤ 8000, папка 5–9
файлов. Справочник `docs/inventory.md` под лимит не подпадает: это данные о
старом коде, а не код. Проверяет `tools/check_limits.py`, границы импортов —
`tools/lint_arch.py`.

## 12. Что считается хорошей архитектурой здесь

Пять проверок, которые можно применить к любому изменению:

1. **Локализация.** Чтобы починить фичу, нужно открыть одну папку.
2. **Одно направление зависимостей.** Импорт «вверх» невозможен без нарушения
   линтера.
3. **Один канал — один перевод.** Новая ветка (MCP, HTTP, CLI) не добавляет
   новой логики, только перевод протокола.
4. **Запись только через воронку.** Нет пути, которым файл меняется мимо плана,
   журнала и предпросмотра.
5. **Контракт явный.** Новая возможность = дескриптор + схема + `kind` ошибок,
   а не «договоримся по ходу».

## 13. Что уточнилось после чтения старого кода

Раскладка выше проверена по коду старого агента (подробности — `docs/mapping.md`).
Что поменялось в этой архитектуре по фактам, а не по названиям файлов:

1. **`formats/`** — в старом агенте было пять парсеров `.gd` и четыре
   разбора `.tscn`. Теперь разбор формата живёт в kernel, а модули им пользуются.
2. **`runtime/`** — `agent_runtime_bridge.gd` работает внутри запущенной игры,
   а не в редакторе: другой хост, другой жизненный цикл, другой профиль отказа.
3. **`editor/harness/`** — headless-прогон (`SceneTree`-скрипт) отделён от
   плагина: его запускает Python, а не панель.
4. **`editor/bridge/verbs/resource/`** и **`verbs/glue/`** — в старой раскладке
   не было места для правок `.tres` и для связки «панель → экзекутор».
5. **`editor/ui/chat/*` и `editor/ui/panel/*`** разрезаны по потокам
   (отправка, подтверждение, план, перезагрузка сцен, вкладки), а не по
   случайным кускам, как `agent_panel_part1..5`.
6. **`code_intel.arch_map` удалён** — это гейт лимитов самого агента, его место
   в `tools/check_limits.py`, а не среди возможностей для проекта игрока.
7. **`context.librarian` удалён** — `librarian` и так единственный владелец `ask`.
8. **`editing.node_ops` удалён** — правки узлов принадлежат сценам
   (`scene_model.node_rename/node_reparent/node_delete`).
9. **43 модуля**, а не «примерно сорок»: по одному на возможность, которую можно
   назвать вслух и проверить тестом.
10. **Политика доступа одна.** В старом коде её считали дважды (`main.py` и
    `agent_bridge.py`) — теперь только `kernel/paths.py`, а каналы её не знают.

## 14. Что уточнилось после второго ревью

Ревью указало на места, где правила описывали границы папок, но не протоколы
взаимодействия. Решения:

| Находка | Решение | Где |
|---|---|---|
| порты не связаны с реализациями; неясно, что получает `setup` | composition root в `runtime/bootstrap.py`, узкий `ModuleContext`, структурная типизация адаптеров, `requires_ports` в манифесте, lifetime по профилю | ADR-0003, R-11 |
| абсолютный запрет межмодульных зависимостей не выдерживает реальности (`context.gather`, `check`) | разрешено публичное API модуля (`__init__.py`) по объявленному `requires`; чужой `domain/` — нельзя; отключение транзитивное | ADR-0004, R-03 |
| `check` в `protocol` нарушал правило | владелец `check` — модуль `verification.check`; остальные дают вклады `contributes_to`; `protocol` только валидирует и вызывает | ADR-0004 |
| у одного инструмента несколько «хозяев» (`write_preview`, `check`, `scene`, `context`) | четыре вида отношений: `provides_tools`, `contributes_to`, `internal_services`, `requires`; конфликт владельцев → `disabled` обоим | ADR-0004, R-05 |
| транзакционная модель не давала обещанной атомарности | WAL до первого эффекта, состояния `PREPARED/APPLYING/COMMITTED`, квитанции шагов, recovery при старте, лок на интервал сверки, `digest`+TTL подтверждения, редакторский батч, защита отката от чужой правки | ADR-0005, R-12 |
| контракт назван и источником, и артефактом; имена смешаны | `ToolSpec` — источник, `contract/*.json` — артефакт; `module_id` / `capability_id` / `tool_name` разведены; `schema_version` | ADR-0006, R-05 |
| `kernel` запрещал Godot, но содержал парсеры `.gd`/`.tscn` | `python/formats/` — разбор форматов без IO и без Godot; в `kernel` только универсальные типы, включая конверт `WritePlan` | R-11, §2 |
| жизненный цикл описывал только happy path | транзитивное отключение, откат частичного `setup`, обратный порядок `teardown`, `degraded` при падении `health`, таймауты и отмена; `environment="editor"` там, где нужен редактор | §7, ADR-0003 |
| R-03 звучал абсолютно («только новая папка») | разграничено: фича на существующих портах и вкладах — папка; новая операция плана / примитив редактора / адаптер — явное расширение контракта | R-03 |
| критерии паритета были жёстче правды | три класса: наблюдаемый паритет, бюджеты производительности, safety-инварианты; лимиты размеров — предупреждения с обоснованием в `deviations.md`; fault-injection на реальной NTFS-копии | R-09, R-06, ADR-0005 |
