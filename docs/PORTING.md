# Перенос механики: пошаговый цикл

Документ описывает **процедуру**, а не архитектуру (та — в `architecture.md`).
Правила, на которые он опирается: R-07 (эталон), R-08 (одна фича — одна
стратегия), R-09 (двойной прогон), R-10 (чек-лист «перенесено»), R-16 (кейсы, а
не тесты), R-17 (`tests-map.md`), R-18 (проверка инструментом), R-19 (статус для
продолжения в другом чате).

## 0. Три источника истины

| Источник | Что даёт | Кто главный |
|---|---|---|
| **Корпус** (`fixtures/corpus/…`) | что старый агент реально отвечал: результат, `kind` ошибки, побочные эффекты | главный для поведения |
| **Старые тесты** | кейсы, граничные входы, история багов (`repro_*`) | источник кейсов, не код |
| **`ToolSpec`** | что новая механика обещает: схема, эффекты, идемпотентность, ошибки | главный для контракта |

Если корпус и старый тест расходятся — верен корпус (тест мог устареть), но
расхождение записывается: возможно, тест фиксирует более новый баг.

## 1. Восемь шагов на одну механику

| Шаг | Действие | Артефакт |
|---|---|---|
| 1 | Взять механику из `PROGRESS.md` (этап `< 7`), посмотреть старый код в `mapping.md` | лист `docs/porting/<module_id>.md` (R-19) |
| 2 | Открыть её строки в `tests-map.md`: семейства тестов и судьба | `docs/tests-map.md` |
| 3 | Снять эталон: прогнать входы через **старый** агент (MCP/HTTP/скрипт) | `fixtures/corpus/<область>/<фича>/*.json` + `manifest.json` |
| 4 | Добавить кейсы из старых тестов, которых нет в эталоне | туда же |
| 5 | Записать спецификацию: `ToolSpec` + инварианты | `modules/<область>/<фича>/tools.py` |
| 6 | Написать тесты нового уровня (unit → contract → integration) | `modules/.../tests/`, `tests/py/contract/` |
| 7 | Написать код: `ports.py` → `domain/core.py` → `app.py` | папка модуля |
| 8 | Получить вердикт: `python tools/selfcheck.py <module_id>` (R-18) | `reports/selfcheck/<module_id>.json` |
| 9 | Двойной прогон корпуса (входит в `selfcheck`, если корпус есть) | CI, `docs/deviations.md` |
| 10 | Живая проверка + запись статуса | лист, `PROGRESS.md`, `WORKLOG.md`, `parity.md` |

Порядок обязателен. Причина: код, написанный до корпуса, проверяется по памяти
автора; корпус, снятый после кода, подгоняется под него незаметно.

## 2. Что именно берётся из старого теста

Берём:

- аргументы вызова (реальные значения: `res://scenes/player.tscn`, `Gun`,
  `Gun/Muzzle`);
- содержимое фикстур: тексты `.tscn`/`.gd`/`project.godot`, которые тест создаёт
  в temp-каталоге;
- ожидаемое наблюдаемое: результат, `kind` ошибки, «файл изменился / не
  изменился / вернулся байт-в-байт»;
- граничные условия, которые тест перечисляет: BOM, CRLF, юникод в путях,
  вложенность, симлинки, пустые файлы;
- для **пишущих** механик — ещё и стиль файла: фикстура обязана содержать хотя бы
  один CRLF-файл и один файл с BOM. Иначе «стиль» и «хеш до правки» проверяются
  только на LF, а разница всплывает у пользователя (так поймано на
  `write_preview`: признак `newline` всегда был `"lf"`).

Не берём:

- `_bootstrap`, `sys.path`, `import main`, `server_state.STATE`,
  `history_manager.set_storage_dir`, `main._remember = lambda …`;
- структуру классов `unittest` и порядок проверок;
- моки внутренних функций (`patch("main._sync_chat_after_reply")`).

## 3. Триаж старых тестов (однократно, затем поддерживается)

Корзины в `tests-map.md`:

| Судьба | Что это | Что делать |
|---|---|---|
| `corpus` | поведение переносимой механики | снять вход и ответ в корпус |
| `ported` | кейсы переехали в тесты нового модуля | ссылка на файл теста в `modules/.../tests/` |
| `replaced` | проверялось только через старый хост (Flask-роут, мост) | заменить на contract/integration нового канала |
| `dropped` | подсистема не переносится (`browser/`, `parsers/`, `minilich/`, `selfcheck.py`) | причина обязательна |
| `deferred` | переносим позже | указать этап |

Файл `tests-map.md` не удаляется и не «чистится»: он и есть доказательство, что
ничего не потеряно.

## 4. Уровни тестов в новом проекте

```
modules/<область>/<фича>/tests/test_core.py   unit: домен без IO, без Godot
tests/py/contract/                            схема ToolSpec, набор kind, отсутствие путей/стектрейсов
tests/py/integration/                         канал → модуль → поддельные адаптеры (MemoryFS, FakeEditor)
tests/py/e2e/                                 MCP/HTTP против живого агента (процесс + сокет)
tests/py/snapshots/                           двойной прогон корпуса: старый ответ == новый ответ
tests/gd/                                     GDScript-примитивы и сцены (headless Godot)
```

Живая (`*_live`) проверка старого проекта переносится как `tests/gd/` или e2e:
она проверяет то, что подделкой не проверить (реальный `.tscn`, undo-скоуп,
перезагрузка сцены).

Корпус бывает двух видов, и путать их нельзя:

| Вид | Где | Что доказывает |
|---|---|---|
| корпус инструмента | `fixtures/corpus/<область>/<фича>/` + `manifest.json` | поведение механики: вход → ответ/ошибка, снято с эталона |
| корпус формата | `fixtures/parity/<формат>/` + `expected.json` | что разбор (`.gd`, позже `.tscn`) совпадает с эталонным парсером |

Оба снимаются **с эталона** (`tools/snapshot_record.py` → `tools/_reference_runner.py`),
а не с нового кода: иначе корпус проверяет сам себя. Фикстуры проектов живут в
`fixtures/projects/<имя>/` и переиспользуются несколькими корпусами.

## 5. Definition of done для механики

- [ ] строка в `parity.md` со статусом `ported`;
- [ ] все строки `tests-map.md` для этой механики имеют судьбу и ссылку;
- [ ] корпус покрывает: happy path, пустой ввод, отсутствующий файл, отказ
      политики, граничный размер;
- [ ] `ToolSpec` описывает эффекты, идемпотентность и полный список `kind`;
- [ ] unit-тесты домена не требуют Godot и файловой системы;
- [ ] contract-тест зелёный, `gen_contract.py --check` без диффа;
- [ ] двойной прогон по корпусу без расхождений (или расхождения в
      `deviations.md`);
- [ ] живая проверка выполнена и описана в `WORKLOG.md` (что делали, что видели);
- [ ] `lint_arch.py` и `check_limits.py` зелёные;
- [ ] `python tools/selfcheck.py <module_id>` вернул `0` (не `1` и не `2`) — R-18;
- [ ] лист `docs/porting/<module_id>.md` и строка в `docs/PROGRESS.md` обновлены;
      «следующее действие» указывает на следующую механику, а не на эту (R-19).

## 7. Отдельно про браузер

Браузерная ветка не входит в первую версию (`parity.md`, `dropped`/`deferred`).
Когда дойдёт очередь: корпус — **записанные кадры протокола** (`ai_studio_net`
protobuf-JSON, `qwen_net` SSE), а не живые сайты. Живая проверка — разовая, вручную,
на провайдере без VPN (DeepSeek); она не является условием паритета, иначе
паритет зависел бы от чужого сервиса.

## 8. Инструменты проверки: свои, а не ручные

Проверка «глазами» не воспроизводима: следующий чат не знает, что запускали.
Поэтому у агента есть два собственных инструмента (R-18).

### `tools/probe.py` — вызвать механику как клиент

```powershell
python tools/probe.py search --args '{"query": "func _ready", "max_results": 5}'
```

Печатает ответ агента как JSON: `{"ok": true, "result": ...}` либо
`{"ok": false, "kind": "not_found", "message": "...", "hint": "..."}`.
Нужен, чтобы увидеть поведение без написания одноразового скрипта и без сборки
клиента. Пока каркаса нет — код возврата `2` и честное сообщение.

### `tools/selfcheck.py` — вердикт по механике

```powershell
python tools/selfcheck.py project_text.search
```

Прогоняет по порядку: границы слоёв (`lint_arch`), лимиты (`check_limits`),
контракт (`gen_contract --check`), unit-тесты, двойной прогон корпуса
(`snapshot_diff`), существование папки модуля и его `tests/`.
Пишет `reports/selfcheck/<module_id>.json`, печатает таблицу.

| Код | Значение |
|---|---|
| `0` | всё зелёное, механику можно двигать дальше |
| `1` | есть провал: код, тесты или корпус разошлись |
| `2` | проверка невыполнима: нет инструмента, нет корпуса, нужен живой Godot (`needs_live`) |

Контракт проверки: инструмент печатает **последней строкой** JSON
`{"status": "ok" | "fail" | "not_implemented" | "needs_live", "detail": "..."}`.
Нет валидного вердикта — считается `not_implemented`: пустая заготовка не бывает
зелёной.

Механики, которым нужен редактор (`node_rename`, `scene_ops`, `resource_ops`,
`editor_context`), получают `needs_live` — это **не** пройденная проверка, а
отметка «живой шаг впереди». Живая проверка остаётся отдельным пунктом DoD.

## 9. Статус: как продолжить в другом чате

Работа может прерваться в любой момент, поэтому состояние живёт в файлах (R-19).

| Файл | Что в нём |
|---|---|
| `docs/PROGRESS.md` | все 44 механики: этап `0…7`, «следующее действие», дата |
| `docs/porting/<module_id>.md` | лист механики: цель, старый код, корпус, кейсы, решения, ход, вердикт `selfcheck`, следующее действие, блокеры |
| `reports/selfcheck/<module_id>.json` | машинный вердикт последнего прогона |
| `docs/WORKLOG.md` | что происходило в сессии и почему |

Правила ведения листа:

- лист создаётся **до** первой правки кода, а не после;
- обновляется в конце каждого шага, а не в конце работы;
- «следующее действие» — одна строка, которую можно выполнить, не читая переписку:
  файл, функция, команда;
- блокер, который не решается сейчас, записывается явно, а не держится в голове.

Порядок восстановления контекста в новом чате:

1. `AGENTS.md` → 2. `docs/PROGRESS.md` (первая механика с этапом `< 7`) →
3. её лист в `docs/porting/` → 4. последняя сессия `docs/WORKLOG.md`.

## 10. Безопасность в цикле переноса (R-20)

Безопасность не «этап после паритета»: она часть контракта механики, иначе её
придётся вставлять в уже работающий код, то есть переписывать.

| Когда | Что делаем |
|---|---|
| Шаг 3 (`ToolSpec`) | заполнить `effects` (`read` / `write_project` / `write_open_scene` / `network` / `process`) и `availability`; для `read` — доказать, что сеть не нужна |
| Шаг 3 | если в механике есть путь из данных во внешний мир — дописать инвариант в `docs/security/invariants.md` (SEC-xx) **до** кода |
| Шаг 6 (код) | никаких `os.system`, `eval`, `exec`, `pickle`, `shell=True`; сеть только через `substrate/llm`; процессы только в `substrate/engine` |
| Шаг 7 (тесты) | тест из `tests/py/security/` для своей механики, если её `effects != read` |
| Шаг 8 (`selfcheck`) | `security` в таблице должен быть `ok`; `fail` — блокер, а не «заметка» |
| Шаг 10 (живая проверка) | проверить, что при отказе агент **fail closed**: нет сети — ошибка `unavailable`, а не тихий обход |

Что механика обязана гарантировать в первой версии (минимум):

1. **Чтение не выходит за проект**: `PathPolicy`, симлинки и junction не
   разыменовываются, `..` отклоняется, `res://`/`user://` разрешаются явно.
2. **Вызов не открывает сеть**, если `effects` не содержит `network`.
3. **Содержимое файлов не исполняется** — ни как код, ни как команда шелла.
4. **Секреты не попадают в вывод**: редакция по шаблонам из `security_audit.py`
   применяется к результату инструмента, ошибке, логу и корпусу.
5. **Ошибка не раскрывает лишнего**: без абсолютных путей домашнего каталога и
   без стектрейсов наружу.

Чего этот раздел не обещает: защиты от вредоносного кода в самом проекте
пользователя (если у него в `.gd` деструктивный код, агент его не исполняет, но и
не лечит), защиты учётной записи провайдера и того, что провайдер увидит
отправленный фрагмент кода — это записано в модели угроз как принятое ограничение.
