# Правила проекта

Файл правил работы над агентом. Здесь фиксируются решения, которые дорого
нарушить: границы, запреты, обязательные договорённости. Правила добавляются
по мере того, как мы их осознанно принимаем, — не задним числом.

Окружение: Godot 4.6 (см. `project.godot`), два языка — GDScript и Python.

## Как пополняется файл

- Каждое правило получает номер: `R-01`, `R-02`, …
- У правила есть три части: **формулировка** → **что это значит на практике** →
  **как проверить нарушение**. Правило без проверки — это пожелание.
- Правило не удаляется молча. Отменённое правило остаётся с пометкой
  `отменено` и указанием причины, иначе через месяц его введут заново.
- Спорные вопросы, по которым решения ещё нет, живут в разделе
  «Открытые вопросы» с номером `Q-01` — чтобы не путать их с правилами.

## R-01. Локализация: весь агент живёт внутри своей папки

**Формулировка.** Весь агент — код, тесты, схемы, документация и вспомогательные
скрипты — находится внутри `addons/godot_agent/`. За пределами этой папки агент
не размещает ничего.

**Что это значит на практике.**

Внутри `addons/godot_agent/` лежит всё без исключения:

- GDScript-часть — в `addons/godot_agent/editor/` (вход плагина, мост, панель,
  настройки);
- Python-часть — в `addons/godot_agent/python/` (домен, возможности, порты,
  адаптеры, каналы, точка входа);
- тесты обоих языков и фикстуры для них;
- схемы протокола (контракт возможностей, словарь примитивов моста);
- документация: архитектура, список паритета, ADR;
- скрипты разработки (проверка границ слоёв, генерация схем, сборка аддона);
- конфиги инструментов, относящиеся к агенту (`pyproject.toml` и подобные).

Ничего из этого не выносится наружу и не скрывается от редактора «чтобы не
мешать»: Python-часть лежит внутри папки плагина, а не рядом с ней.

В корне проекта остаётся только то, что требует сам Godot: `project.godot`,
`icon.svg`, `.gitignore`, `.editorconfig`, `.gitattributes`. Ни `src/`,
ни `python/`, ни `tests/`, ни `docs/`, ни `tools/` на верхнем уровне не
появляются.

**Почему так.**

1. Папка плагина — это единица поставки. Плагин копируется, удаляется и
   сравнивается целиком; всё, что лежит снаружи, при переносе теряется.
2. Два плагина рядом не должны делить ни одного файла: общий код = общая
   деградация и невозможность удалить один, не задев другой.
3. Границу видно глазами: всё, что относится к агенту, — в одной папке,
   и это же место отвечает на вопрос «где искать».

**Как проверить нарушение.**

Корень проекта содержит только файлы Godot-проекта; поиск по проекту не
находит агентских артефактов вне `addons/godot_agent/`. Проверка будет
автоматизирована скриптом внутри папки плагина (см. будущий `R-…` о
проверках), но правило действует с текущего момента и без скрипта.

## R-02. Одна фича — одна папка

**Формулировка.** Каждая возможность агента живёт в собственной папке
`addons/godot_agent/python/modules/<область>/<фича>/`. Папка самодостаточна: в ней
весь код фичи, её схемы, настройки и тесты. Файлы фичи не лежат россыпью по
общим каталогам.

**Что это значит на практике.** Состав папки одинаков во всех модулях — чтобы
искать по имени, а не вспоминать, где это было:

```
addons/godot_agent/python/modules/<область>/<фича>/
├─ module.py     # манифест модуля (см. R-05)
├─ tools.py      # ToolSpec: имена, схемы, эффекты
├─ app.py        # сценарий: валидация → домен → порты → результат
├─ ports.py      # что фиче нужно от мира (typing.Protocol); появляется с первым потребителем
├─ domain/       # чистые правила фичи, без платформы
├─ settings.py   # только если у фичи есть настройки
└─ tests/        # unit + contract + fixtures
```

Правила имён:

- имя папки модуля = имя фичи = первая часть `id` модуля;
- имена файлов одинаковы во всех модулях (`module.py`, `tools.py`, `app.py`);
- запрещены имена `utils.py`, `helpers.py`, `common.py`, `misc.py`: если
  хочется так назвать файл, значит код принадлежит `shared` области или
  `kernel` — либо это две разные фичи, которые надо разделить;
- файлы фичи не кладутся в чужие папки «временно»: временное живёт до ревью,
  а не до следующего релиза.

**Почему так.** Единый шаблон делает любой модуль читаемым с первого взгляда:
«сломалось вот это» → открывается папка, в ней пять предсказуемых имён. Это
же свойство нужно и ИИ-агенту: он находит код фичи по имени, а не поиском по
всему проекту.

**Как проверить нарушение.** У каждого модуля есть `module.py`, `tools.py` и
`tests/`; ни в одном модуле нет файлов из запрещённого списка имён; ни один
файл фичи не находится вне папки своей фичи.

## R-03. Модульность: подключение без правок снаружи, удаление без поломок

**Формулировка.** Фича на существующих портах и вкладах подключается и
отключается только содержимым своей папки: регистрация не требует правок в
общем коде, удаление папки модуля не ломает агент. Расширение платформенного
API (новый примитив редактора, новый адаптер, новый вид операции плана) —
отдельное явное изменение с версией контракта, а не «фича в своей папке».

**Что это значит на практике.**

- Загрузчик обнаруживает модули сканированием
  `addons/godot_agent/python/modules/*/*/module.py`.
  Регистрация = наличие папки. «Пара строк в главном файле» не нужна: правок
  вне папки модуля — ноль. Принудительный порядок или отключение — это
  настройка (`disabled_modules`), а не правка кода.
- Модуль не импортирует `domain/`, `app.py` и внутренние файлы другого модуля.
  Разрешён импорт **публичного API** — только того, что реэкспортировано в
  `__init__.py` модуля и объявлено в `requires` (ADR-0004). Всё остальное —
  нарушение границы, даже если «просто функция».
- Зависимость транзитивна: отключили или удалили обязательную зависимость —
  зависимые модули тоже уходят в `disabled` с причиной, а не падают при первом
  вызове.
- Ошибка импорта, исключение в точке входа, цикл зависимостей, конфликт имён
  инструментов, несовместимая версия ядра — модуль получает состояние
  `disabled` с причиной, агент стартует дальше. Один сломанный модуль не
  валит остальные.
- Состояние модулей видно снаружи: `id`, версия, `enabled/disabled`, причина,
  список возможностей и вкладов.
- Вызов инструмента выключенного или удалённого модуля различается по
  состоянию реестра: имя известно, но владелец недоступен → `unavailable` с
  причиной и подсказкой; имени нет ни в реестре, ни в контракте → `unknown_tool`.
  Реестр помнит имена из `contract/`, поэтому «удалили папку» даёт
  `unavailable`, а не «такого никогда не было».

**Почему так.** Это прямое требование к проекту: фичу можно выключить или
удалить, не выпиливая её из кода и не рискуя остальным. Плюс модульность даёт
параллельную работу — два модуля в разных папках почти не конфликтуют.

**Как проверить нарушение.** Тест: удалить папку модуля → агент стартует,
остальные инструменты работают, статус без ошибок. Тест: сломать `module.py`
→ модуль в `disabled` с причиной. Линтер: импорт из одного модуля в другой
запрещён.

## R-04. Одна логика — много веток

**Формулировка.** Логика возможности реализуется ровно один раз — в модуле.
Ветки агента (MCP, HTTP/API, браузерная часть, панель в редакторе, CLI) —
тонкие переводчики протокола и не содержат собственной реализации правил.

**Что это значит на практике.**

- Ветка делает только это: принять запрос → проверить по схеме → вызвать
  сценарий модуля → отдать результат в своём формате. Никаких алгоритмов.
- Ни одна ветка не имеет права на свою копию фичи «потому что так удобнее».
  Вторая реализация одной возможности = дефект архитектуры, лечится переносом
  логики в модуль, а не синхронизацией двух копий.
- Нейросеть — клиент, а не слой. В модулях нет ни одного признака «это вызвал
  ИИ»: возможность одинаково работает и с моделью, и без неё.
- Средозависимое (открытые сцены, undo/redo) живёт как редакторные примитивы,
  а не как второй вариант той же логики.
- Если ветке нужно то, чего нет в модели возможностей, — добавляется
  возможность в модуль. Обходной путь внутри ветки запрещён.

**Почему так.** Это ровно то свойство, ради которого проект пересобирается:
одна чистая функция на все входы. Четыре копии — это четыре поведения,
четыре бага и четыре места для правки.

**Как проверить нарушение.** Поиск по `channels/` и `editor/` не находит
разбора `.gd`/`.tscn`, построения планов правки, линта и прочей логики фич.
Для каждой возможности в проекте существует ровно одна реализация.

## R-05. Манифест модуля — единственное, что знает общий код

**Формулировка.** Общий код знает о модуле только его манифест. Всё остальное
внутри папки модуля приватно.

**Что это значит на практике.** Манифест объявляет:

- `id` в виде `область.фича` — стабильный неймспейс, не меняется при
  рефакторинге;
- `version` (semver) и диапазоны совместимости: `kernel_api`, `godot`;
- `environment` — где модуль существует: `editor`, `headless`, `cli`;
- `entrypoints` по средам вместо единственного `setup`;
- `provides_tools` — публичные имена, у которых модуль **владелец** (`check`,
  `read`): каждое имя принадлежит ровно одному модулю, конфликт → `disabled`
  обоим кандидатам (ADR-0004);
- `contributes_to` — вклад в **чужой** составной инструмент (`check`, `context`,
  `scene`, `write_preview`), без публикации своего имени;
- `internal_services` — возможности без публичного имени: HTTP-маршрут, кнопка
  панели, снимок рантайма; канал подключается по манифесту, а не импортом;
- отношения с другими модулями по `module_id`: `requires` (влияет на
  транзитивное отключение), `recommends`, `suggests`, `conflicts`, с диапазонами
  версий;
- `requires_ports` — какие порты нужны от композиции (`fs`, `editor`, `engine`,
  `store`, `clock`; ADR-0003);
- `capabilities` — свои capability id, а не схемы: схемы живут в `ToolSpec`
  (ADR-0006);
- `settings_schema` — настройки с префиксом `id` модуля;
- `health()` и `teardown()`.

Требования:

- импорт модуля без побочных эффектов: файлы, сеть, сокеты — только в точке
  входа, иначе обнаружение модуля начнёт менять состояние агента;
- имена инструментов и ключи настроек уникальны; коллизия — детерминированный
  отказ на старте, а не «кто последний, тот и прав»;
- несовместимая версия → `disabled` с причиной, а не падение.

**Почему так.** Дисциплина взята у проверенных платформенных решений (реестр
модов): манифест, неймспейсы, диапазоны версий, несколько точек входа. Это
единственный способ, чтобы «старый модуль в новой версии агента» деградировал
предсказуемо.

**Как проверить нарушение.** Манифест валидируется схемой; тест ловит
дубликаты имён инструментов; модуль без точки входа не загружается; импорт
модуля не выполняет IO (проверяется тестом на обнаружение).

## R-06. Лимиты размеров

**Формулировка.** Размер — часть архитектуры. Превышение лимита означает, что
граница проведена неверно, и лечится разделением, а не «пока так».

**Что это значит на практике.**

- файл ≤ 400 строк — **жёсткий** предел для нового файла;
- `module.py` / `tools.py` ≤ 150;
- модуль с несколькими инструментами (`provides_tools` длиной > 1) держит схему
  каждого инструмента в своём файле (`tools_<tool>.py`), а `tools.py` только
  собирает `TOOLS` — иначе второй инструмент упирается в лимит и начинается
  «резка по размеру» (это уже случилось на втором инструменте `code_intel.usages`);
- `app.py` ≤ 80 строк: только оркестрация (валидация → домен → порты → результат),
  правила живут в `domain/`; оркестрация не «дорастает» до логики;
- модуль ≤ 3000, область ≤ 8000, папка 5–9 элементов — **предупреждения**:
  превышение допустимо один раз и только с записью в `docs/deviations.md`, где
  объяснена связность (cohesion), а не «так удобнее»;
- деление «по размеру» без потери смысла — не улучшение: сначала ищется граница
  (фича, вклад, операция), потом режется;
- лимит 400 строк не распространяется на `docs/inventory.md`: это справочник по
  старому коду (данные), а не код;
- `kernel` не растёт: если в нём появилось «про сцены» или «про MCP», это
  утечка — код переезжает в область.

**Почему так.** 60k строк держатся в порядке только за счёт предсказуемого
размера единиц: маленький модуль можно переписать целиком, большой — только
патчить.

**Как проверить нарушение.** Скрипт в CI считает строки по файлам, модулям и
областям и падает при превышении.

## R-07. Эталон снимается до переноса

**Формулировка.** Ни одна возможность не переносится, пока с работающего старого
агента не снят эталон её поведения: входы, выходы, ошибки и побочные эффекты.
Эталон — единственное доказательство, что перенос не сломал функцию.

**Что это значит на практике.**

- Корпус входов: реальные файлы проекта (образцы `.gd`, `.tscn`), краевые
  случаи (пустой файл, битая сцена, отсутствующий путь, очень большой файл) и
  типичные запросы. Хранится в `fixtures/corpus/` с манифестом: запрос, вход,
  ожидание.
- Эталон фиксирует **четыре** вещи, а не только «правильный ответ»: результат,
  тип и код ошибки, побочные эффекты (какие файлы изменились, что попало в
  журнал), структуру ответа.
- Нормализация обязательна: абсолютные пути → относительные, коллекции →
  сортировка, идентификаторы → стабильные, время/версии/случайность → вырезаны.
  Нестабильный снапшот хуже отсутствующего: его перестают читать.
- Снапшоты коммитятся в репозиторий и прогоняются против **старого** агента в
  CI: изменение эталона — осознанный коммит, а не «само обновилось».
- Ошибки старого агента тоже эталон. Багованное поведение фиксируется в списке
  отклонений (R-09) и чинится отдельно, а не «заодно при переносе».

**Почему так.** Уверенность не берётся из аккуратности переноса. Она берётся из
сравнения с зафиксированным поведением.

**Как проверить нарушение.** У каждой возможности в `docs/parity.md` есть
ссылка на снапшот. Возможность помечена «перенесена» без снятого эталона —
нарушение R-07.

## R-08. Один перенос — одна фича, одна стратегия

**Формулировка.** Переносится ровно одна возможность за коммит, по заранее
выбранной стратегии и отдельно от любых улучшений.

**Что это значит на практике.** Три допустимые стратегии; выбранная
указывается в шапке файла:

- **по спецификации** — переписать заново по описанию входа/выхода/эффектов
  (по умолчанию);
- **дословно** — скопировать алгоритм, где ценность в деталях (парсер `.tscn`,
  лексер `.gd`, правила линта); помечается `ported verbatim`, с указанием
  исходного файла и коммита, и покрывается собственным снапшотом;
- **обёртка** — временный вызов старого кода из новой архитектуры; обязателен
  срок снятия и запрет обрастать логикой.

Запреты:

- смешивать стратегии в одном файле;
- смешивать перенос с исправлением багов, рефакторингом и новыми функциями —
  найденный баг идёт в список и чинится отдельным изменением со своим тестом;
- переносить «пакетами» по пять фич: при расхождении непонятно, что сломалось;
- править старый плагин, чтобы облегчить перенос (старый код — музей, R-01
  и договорённость о заморозке).

**Почему так.** Пока перенос и улучшение в одном коммите, любое отличие от
эталона неотличимо от намеренного изменения, и аргумент «я так задумал» убивает
доверие к тестам.

**Как проверить нарушение.** Коммит содержит один ID возможности и одну
стратегию; в сообщении есть ссылка на снапшот; diff не содержит правок старого
плагина.

## R-09. Эквивалентность доказывается сравнением, а не ревью

**Формулировка.** Перенос корректен, когда новый код автоматически сравнён с
эталоном на всём корпусе, и каждое расхождение объяснено.

**Что это значит на практике.**

- **Двойной прогон (differential):** один корпус — через старый и новый
  вариант, отчёт — список расхождений. Пока расхождения не разобраны,
  возможность не перенесена.
- **Инварианты для чистых функций:** parse → serialize возвращает исходный
  текст; preview не меняет файлы (хеши до/после); apply + rollback возвращает
  байт-в-байт; повторный вызов идемпотентной операции не меняет состояние.
- **Расхождения бывают только двух видов:** баг переноса (чиним) или
  осознанное отклонение (запись в `docs/deviations.md` с причиной, снапшот
  помечается ожидаемым отличием). Третьего не бывает.
- **Регрессией считается расхождение в наблюдаемом:** значение результата, тип
  ошибки, состояние проекта, побочные эффекты (какие файлы изменились и как).
  Порядок полей в ответе и число системных вызовов сами по себе регрессией не
  являются — это бюджеты.
- **Три класса проверок не смешиваются:**
  1. *наблюдаемый паритет* — сравнение со старым агентом; расхождение → баг или
	 `deviations.md`;
  2. *бюджеты производительности* — время и объём I/O по классам операций
	 (чтение, анализ, запись, headless); отдельные пороги, а не побайтовое
	 совпадение: WAL, блокировки и recovery законно добавляют I/O;
  3. *safety-инварианты*, которых в старом агенте не было: recovery после
	 падения, повторный `apply`, `rollback` после внешней правки, конкуренция
	 двух сессий. Эталон здесь — ADR-0005, а не старый код.
- **Тест не подгоняется под реализацию.** Если для прохождения пришлось
  ослабить ассерт, добавить `skip`/`xfail` или удалить проверку — это
  регрессия, оформленная как «тест сломался», а не как «тест починили».
- **Мутационная проверка для критичных участков** (планы правки, политика
  путей, откат): намеренная поломка должна ронять тест. Тест, который не падает
  при поломке, считается отсутствующим.

**Почему так.** Ревью и «вроде работает» не масштабируются на 60k строк.
Масштабируется только автоматическое сравнение.

**Как проверить нарушение.** Отчёт двойного прогона приложен к переносу; в
`docs/deviations.md` нет записей без причины и одобрения; в истории нет
коммитов вида «поправил тест, чтобы прошёл».

## R-10. «Перенесено» — это чек-лист, а не ощущение

**Формулировка.** Возможность считается перенесённой только при выполнении всех
пунктов ниже. Пункт без галочки означает, что возможность остаётся в старом
агенте.

**Что это значит на практике.** Для каждой возможности:

1. ID в `docs/parity.md` и статус (`must` / `should` / `drop`);
2. эталон снят со старого агента и лежит в репозитории (R-07);
3. спецификация: входы, выходы, эффекты, известные ограничения;
4. реализация ровно одна, в папке фичи (R-02), стратегия указана (R-08);
5. двойной прогон без необъяснённых расхождений (R-09);
6. contract-тест: имя инструмента, схема, коды ошибок;
7. домен без импортов платформы и без прямых обращений к диску;
8. лимиты размеров соблюдены (R-06);
9. для поведения, живущего в редакторе (открытые сцены, undo/redo), — прогон
   в живом редакторе с отметкой «проверено вручную: дата, чем»;
10. старый плагин не изменён, а возможность в нём помечена как перенесённая.

Честная оговорка: для поведения, зависящего от среды редактора, «100%»
автотестом не доказывается — там эквивалентность подтверждается контрактом,
дымовым прогоном и ручной отметкой с ограниченным сроком годности
(перепроверяется при каждом изменении соответствующего примитива).

**Почему так.** Чек-лист — единственный способ не спорить «готово или нет» и не
терять функции при пересборке.

**Как проверить нарушение.** У каждой записи parity-листа есть все галочки либо
явная причина исключения; CI проверяет наличие снапшотов и отчёта двойного
прогона.

## R-11. Направление зависимостей и швы

**Формулировка.** Зависимости идут только внутрь: `channels` → `protocol` →
`modules` → `formats` → `kernel`. Платформа и транспорт живут на краях. Порт
объявляет потребитель, а не реализация; связывает их композиция
(`runtime/bootstrap.py`, ADR-0003).

**Что это значит на практике.**

- `kernel` не импортирует ничего, кроме стандартной библиотеки, и не содержит
  ни строчки про сцены, транспорт или Godot.
- Модуль может импортировать `shared` своей области, `formats`, `kernel` и
  **публичное API** другого модуля (`__init__.py`, только если объявлено в
  `requires`). Модуль не импортирует чужой `domain/`/`app.py`, `substrate`,
  `protocol`, `channels`, `editor`.
- C.12 (ADR-0010): только `verification.api_check/app.py` может импортировать
  точное имя `python.modules.engine_kb.shared.inheritance`. Это узкий чистый
  шов сборки членов, не разрешение чужих `shared` вообще; `domain/` исключения
  не получает. Файл-поставщик остаётся неизменным; разрешение проверяет линтер.
- Порт объявляется в `ports.py` модуля (`typing.Protocol`) и реализуется
  `substrate` **структурно**: адаптер не импортирует `modules`, модуль не
  импортирует адаптер. Связывает их `runtime/bootstrap.py` — единственное место,
  которое знает обе стороны (ADR-0003). Соответствие проверяется тестом контракта
  (`@runtime_checkable` + `isinstance`).
- `formats` — разбор `.gd` и `.tscn` без IO и без Godot: им пользуются модули и
  адаптеры, сам он не знает ни про сцены, ни про возможности. В `kernel`
  Godot-специфики нет: только универсальные типы агента (ошибки, пути, diff,
  `ToolSpec`, конверт `WritePlan`).
- Описание возможности (`ToolSpec`) — это данные, поэтому тип живёт в `kernel`.
  `protocol` только собирает реестр из модулей и генерирует схемы: наоборот
  нельзя, иначе модулю придётся импортировать `protocol` и направление
  сломается.
- Каналы не импортируют `substrate` напрямую — только через сборку
  (`runtime`/`bootstrap`).
- Циклы запрещены. Слои проверяются линтером, а не памятью.
- Обход слоя «на минутку» запрещён: если очень нужно — значит шов проведён
  неверно, и это исправляется, а не обходится.

**Почему так.** Это единственный закон, который даёт тесты без платформы и
позволяет заменить адаптер, не трогая домен. Пока он держится с первого файла,
он дешёвый; после двадцатого модуля — уже нет.

**Как проверить нарушение.** Линтер импортов в CI: правила выше проверяются
машиной; граф зависимостей ацикличен; в
`addons/godot_agent/python/modules/*/*/domain/` нет импортов,
выполняющих IO (`os`, `pathlib`, `socket`, `subprocess`) и внутренних пакетов
платформы.

## R-12. Одна воронка записи

**Формулировка.** Ни один код не пишет в проект напрямую. Любая правка проходит
через единственный механизм: план → предпросмотр → применение → журнал → откат.

**Что это значит на практике.**

- Стадии: `validate` → `prepare` (план, `digest`, `expected`, запись в WAL) →
  `preview` (отдаёт `plan_id`) → `apply` (под локом: перечитать состояние,
  сверить, применить, писать квитанции) → `COMMITTED` → `rollback` по квитанциям
  (ADR-0005).
- WAL пишется **до** первого побочного эффекта, квитанция шага — после эффекта и
  до следующего шага. Падение процесса на любом шаге восстанавливается при
  старте, а не оставляет проект половинчатым.
- Атомарность: план применяется целиком или не применяется вовсе — включая
  смешанные планы «несколько файлов + открытая сцена + `project.godot`».
  Проверка состояния и применение идут в одном неделимом интервале под
  per-project локом.
- Идемпотентность: повторный `apply` того же `plan_id` не применяет план
  второй раз; повторный `rollback` — типизированная ошибка, а не тихое
  повторение.
- Устаревший план: `apply` проверяет, что исходное состояние не изменилось с
  момента предпросмотра (хеши/версии), иначе `stale_plan`.
- Вид правки (файл, узел сцены, символ, split) — это операция внутри плана, а
  не отдельная реализация со своим откатом.
- Правки открытых сцен идут туда же: план строится в домене, применяется
  примитивом редактора с undo-скоупом.
- Прямая запись файла (`open(..., "w")`, `FileAccess`, `DirAccess`) вне воронки
  запрещена. Исключение — сама воронка и её тестовые двойники.

**Почему так.** Агент правит чужой проект. Половина применённой правки или
неработающий откат — это необратимый урон для пользователя, а не «неудобство».

**Как проверить нарушение.** Поиск операций записи по проекту находит только
воронку. Тесты: сбой на середине плана не меняет проект; `apply` + `rollback`
возвращает байт-в-байт; повторный `apply` не меняет ничего.

## R-13. Политика путей и разрушающие операции

**Формулировка.** Доступ к файлам разрешается в одном месте. Необратимые
операции невозможны без предварительного предпросмотра.

**Что это значит на практике.**

- `PathPolicy` — единственное место, где решается, что можно читать и писать:
  только внутри проекта, кроме служебных папок; запрещены системные пути,
  выход через `..`, абсолютные пути вне проекта, симлинки наружу.
- Все входные пути нормализуются до сравнения. Проверка «по строке» без
  нормализации не считается проверкой.
- Разрушающие операции (удаление узла, перезапись файла, массовое
  переименование) выполняются только после `preview` с явным подтверждением.
  Без подтверждения — `denied`.
- Отказ всегда типизированный (`denied` + причина). «Молча ничего не сделал» —
  запрещённый вариант поведения.
- Ограничения — данные (конфиг), а не разбросанные по коду условия: сузить
  права можно без правки модулей.

**Почему так.** Это защита не от багов, а от необратимых действий в чужом
проекте. Один такой случай перевешивает год экономии на проверках.

**Как проверить нарушение.** Тесты на обход: абсолютный путь, `..`, симлинк
наружу, путь вне проекта → `denied`. Поиск по проекту: ни один модуль не
сравнивает пути сам, вся проверка — в единственном месте.

## R-14. GDScript-сторона: мост — руки, не голова

**Формулировка.** Слой в редакторе предоставляет примитивы и UI, но не
реализует логику фич.

**Что это значит на практике.**

В `editor/` разрешено:

- примитивы: дерево сцены, открытые сцены, выделение, undo-скоуп, выполнение
  в главном потоке, прогресс и подтверждение;
- транспорт (сокет, фрейминг, диспетчеризация), настройки плагина, UI панели.

В `editor/` запрещено:

- разбор `.gd` и `.tscn`, линт, построение diff, построение планов, политика
  путей и любые алгоритмы фич — всё это Python;
- прямая запись файлов проекта из GDScript, кроме применения готового плана,
  полученного от Python;
- «понимание» домена: мост не решает, как переименовать узел, он применяет
  полученные операции;
- собственная классификация ошибок и собственные форматы ответов.

Требования:

- один примитив — одно действие; словарь примитивов маленький (порядка 10–15)
  и меняется редко;
- список примитивов совпадает с `contract/editor_verbs.json`;
- данные передаются без интерпретации: GDScript не пересобирает структуры.

**Почему так.** При двух языках главный риск деградации — «второй вариант
логики», который расходится с основным. Через полгода никто не помнит, где
правильная версия.

**Как проверить нарушение.** В `editor/` нет разбора `.gd`/`.tscn`, нет
построения планов и diff; список примитивов совпадает с контрактом; ни одна
фича не имеет реализации на GDScript.

## R-15. Типизированные ошибки

**Формулировка.** Ошибка — это данные, а не строка. Код ошибки стабилен и
одинаков во всех ветках.

**Что это значит на практике.**

- Единая форма: `kind` (машиночитаемый код), `message` (человеку), `hint` (что
  делать), `details` (контекст: путь, символ, план).
- Базовый набор `kind`: `invalid_input`, `not_found`, `denied`, `stale_plan`,
  `conflict`, `engine_down`, `unavailable`, `internal`, `unknown_tool`.
- `unavailable` и `unknown_tool` — не одно и то же: первое значит «имя известно,
  владелец недоступен, есть смысл повторить позже», второе — «такого инструмента
  нет, исправляйте вызов». Реестр помнит имена из `contract/`, поэтому удалённый
  модуль отвечает `unavailable` с причиной, а не притворяется несуществующим.
- Домен возвращает `kind`; канал только упаковывает его в свой протокол.
  Классификация ошибок существует в одном месте.
- `internal` — только для настоящих багов. Всё ожидаемое имеет собственный
  `kind`: «файла нет» и «политика запретила» — разные вещи с разной реакцией.
- В ответе клиенту нет стектрейсов и абсолютных путей.
- Новый `kind` добавляется осознанно и попадает в контракт.

**Почему так.** Веток много, клиенты внешние. Пока ошибка — текст, клиент
угадывает по словам, а тесты проверяют формулировки вместо поведения.

**Как проверить нарушение.** Contract-тест перечисляет допустимые `kind` и
падает на неизвестном; каналы не содержат своей классификации; ответы не
содержат путей и стектрейсов.

## R-16. Старый тест — источник кейсов, а не файл для копирования

**Формулировка.** При переносе из старого плагина переносится **кейс** (вход,
ожидаемое наблюдаемое, побочные эффекты), а не код теста. Новый тест пишется в
терминах новой архитектуры и не импортирует ничего из старого проекта.

**Что это значит на практике.**

- Из старого теста берём: аргументы вызова, содержимое фикстур (`.tscn`, `.gd`,
  `project.godot`, файлы данных), ожидаемый результат, ожидаемый `kind` ошибки,
  ожидаемые побочные эффекты («файл изменился / не изменился / откатился
  байт-в-байт»).
- Из старого теста **не** берём: `import main`, `server_state`, `_bootstrap`,
  `history_manager.set_storage_dir`, monkeypatch внутренних функций хоста,
  структуру классов и порядок проверок. Всё это описывает старую архитектуру и
  нарушает R-11 ещё до первого запуска.
- Порядок работы: **корпус → спецификация → тесты → код**. Корпус — первичен,
  потому что это буквально ответ старого агента; тест — вторичен, потому что это
  чьё-то мнение о поведении, и часть мнений устарела.
- `repro_*`-тесты старого проекта — самые ценные файлы: они фиксируют историю
  багов. Каждый обязан стать записью корпуса, иначе баг вернётся незамеченным.
- Старый проект в новой работе — только для чтения: его тесты не редактируются и
  не запускаются как часть нового набора.
- Новый тест не «переписывается» из старого: он пишется из спецификации
  (`ToolSpec` + инварианты). Совпадение имён тестов с прошлыми случайно и
  смысловой нагрузки не несёт.

**Почему так.** Тест-файл кодирует архитектуру, кейс кодирует поведение. Копия
файла тянет `main`, глобальное `STATE` и патчи внутренностей, после чего новая
архитектура начинает защищать старые границы. Проверено на этом же проекте: 148
из 168 старых тестов подключают `_bootstrap`, 25 импортируют `main`, 42 несут
метки прошлой перестройки.

**Как проверить нарушение.** Грепом по новым тестам: нет `_bootstrap`,
`server_state`, `import main`, `godot_tools`, `history_manager`. У каждого
`repro_*` старого проекта есть соответствующая запись в корпусе.

## R-17. Ни один старый кейс не исчезает молча

**Формулировка.** Каждый старый тест получает судьбу в `docs/tests-map.md`.
Отсутствие строки — это потеря покрытия, а не «не успели».

**Что это значит на практике.**

- `docs/tests-map.md` — таблица: файл старого теста, механика (новый модуль или
  `?`), семейство (`unit` / `flow` / `live` / `repro` / `helper`), судьба,
  причина.
- Судьба — одно из: `ported` (кейсы живут в тестах нового модуля), `corpus`
  (снято в корпус как эталон), `replaced` (проверяется на другом уровне: contract
  или e2e), `dropped` (подсистема не переносится — с причиной), `deferred`
  (переносится позже, с указанием этапа).
- Появился новый файл в старом `tests/` — появилась строка. Строки не удаляются:
  судьба может меняться, история остаётся.
- `dropped` допустимо только для выброшенной подсистемы и только с причиной
  («browser: нужен VPN для AI Studio», «minilich: не входит в агент»).
- Статус модуля в `docs/parity.md` не может стать `ported`, пока его строки в
  `tests-map` остаются без судьбы.

**Почему так.** Тихая потеря фичи — самый дорогой дефект переноса: тесты старые
удалены, новых нет, и никто не знает, что проверка исчезла (продолжение R-10).

**Как проверить нарушение.** Число строк в `docs/tests-map.md` (кроме заголовков
и пустых) не меньше числа старых файлов `tests/*.py`; каждая строка имеет
заполненную судьбу; у каждого `dropped` есть причина.

## R-18. Проверка — инструментом, а не руками

**Формулировка.** У агента есть собственные инструменты проверки. Если их нет —
они пишутся первыми, а не заменяются ручным запуском команд и чтением вывода.

**Что это значит на практике.**

- `tools/probe.py` — вызвать **одну** механику нового агента так, как это сделает
  клиент: аргументы, ответ, `kind` ошибки. Нужен, чтобы увидеть поведение, не
  собирая руками Python-однострочник.
- `tools/selfcheck.py <module_id>` — прогнать проверки механики и получить
  **вердикт**: границы слоёв, лимиты, контракт, unit, contract, двойной прогон
  корпуса. Пишет `reports/selfcheck/<module_id>.json`, печатает таблицу,
  возвращает код: `0` — всё зелёное, `1` — есть провал, `2` — проверка не может
  быть выполнена (нет корпуса, нет инструмента, нужен живой Godot).
- Механике, которой нужен живой редактор, `selfcheck` ставит `needs_live`. Такая
  строка **не считается пройденной**: живая проверка остаётся отдельным шагом.
- Вердикт прикладывается к отчёту о работе. Отчёт без вывода `selfcheck`
  не принимается — «проверил глазами» доказательством не является.
- Инструмент проверки — часть работы, а не инфраструктура «потом»: без него
  следующий шаг проверяется памятью автора.
- Проверка идёт **по модулю, а не по имени фичи**: если модуль владеет
  несколькими инструментами (`provides_tools`), в прогон входят **все** его
  корпуса и все его инструменты. Обратное уже случалось дважды: сначала
  `selfcheck` был зелёным на пустой заготовке, затем `snapshot_diff` молча
  выбрасывал второй инструмент модуля из прогона. Инструмент проверки, который
  не видит часть работы, хуже отсутствующего: он выдаёт вердикт.

**Почему так.** Ручная проверка не воспроизводима: следующий чат не знает, что
именно запускали, и не может повторить. Инструмент делает проверку дешёвой, и
поэтому её делают, а не пропускают.

**Как проверить нарушение.** В отчёте нет таблицы `selfcheck`; механике нужен
редактор, а `needs_live` нигде не отмечен; проверка выполнялась скриптом,
которого нет в `tools/`.

## R-19. Статус механики пишется для продолжения в другом чате

**Формулировка.** Перенос механики — это работа, которую можно прервать в любой
момент. Поэтому её состояние живёт в файлах, а не в переписке.

**Что это значит на практике.**

- `docs/PROGRESS.md` — индекс всех механик: этап (`0`…`7`), следующее действие,
  дата обновления. Одна строка на модуль, ничего не удаляется.
- `docs/porting/<module_id>.md` — рабочий лист механики: цель, старый код, корпус,
  кейсы из старых тестов, принятые решения, ход (дата → шаг → результат),
  последний вердикт `selfcheck`, **следующее действие одной строкой**, блокеры.
- Лист создаётся **до** первой правки кода и обновляется в конце каждого шага,
  а не в конце работы.
- «Следующее действие» формулируется так, чтобы его можно было выполнить, не
  читая переписку: файл, функция, команда.
- Новый чат начинает с `AGENTS.md`. Для назначенной задачи читает относящиеся
  к ней правила и лист; для продолжения работы — её строку `PROGRESS.md`, лист
  и последнюю связанную запись `WORKLOG.md`. Первую механику с этапом меньше `7`
  выбирает только при продолжении плана переноса без отдельной задачи (ADR-0094).

**Почему так.** Самая дорогая потеря — не код, а понимание, на чём остановились:
без листа следующий чат начинает механику заново или, хуже, «улучшает» уже
готовое.

**Как проверить нарушение.** У механики есть коммит, но нет листа; лист не
обновлялся дольше последней правки кода; в `PROGRESS.md` этап расходится с
фактом (например, `ported` без вердикта `selfcheck` и живой проверки).

## R-20. Безопасность — часть контракта

**Формулировка.** Агент не должен давать третьей стороне больше прав, чем дал бы
пользователь сам: он не выполняет чужой код, не пишет вне проекта, не слушает
сеть без нужды, не хранит секреты в открытом виде и не отправляет наружу то, что
не нужно для ответа.

**Что это значит на практике.**

- Модель угроз обязательна (`docs/security/threat-model.md`), инварианты
  пронумерованы (`docs/security/invariants.md`, SEC-01…). Новый инструмент с
  эффектом добавляет инвариант и тест, а не «надеемся на лучшее».
- **Сеть по умолчанию выключена.** MCP — stdio (процесс запускает клиент). HTTP —
  только по явному включению, только `127.0.0.1`, случайный порт в
  `user://godot_agent/port.json`, обязательный токен, отказ при чужом `Origin`,
  неизвестном `Host` и теле больше лимита. Причина: localhost доступен любому
  процессу и любой странице в браузере (DNS rebinding, CSRF через fetch).
- **Список хостов — данные** (`contract/network_allow.json`): домены провайдеров
  LLM и ничего больше. Хост вне списка → `denied`, а не «попробуем». Приватные
  адреса (`127.*`, `10.*`, `192.168.*`, `169.254.*`, `*.local`) запрещены всегда:
  это SSRF в локальную сеть и к metadata-сервисам.
- **Один слой наружу** — `substrate/llm/*`. Остальной код не импортирует
  `socket`, `urllib`, `http.client`, `requests`; проверяется линтером.
- **Запуск процессов** — только `substrate/engine/headless_runner.py`:
  фиксированный argv, без `shell=True`, пользовательская строка не становится
  командой. `os.system`, `eval`, `exec`, `pickle` запрещены в `python/`.
- **Секреты** — не в проекте и не в git: только `user://godot_agent/` или
  переменные окружения; в логи, отчёты и корпус не попадают (редакция по
  шаблонам `sk-`, `AIza`, `ghp_`, `Bearer`).
- **Данные ≠ инструкции.** Содержимое файлов, ответы инструментов, текст из сети —
  данные. Команды из них не выполняются. Автоподтверждение записи включается
  только настройкой пользователя и никогда — содержимым проекта.
- **Провайдер LLM видит отправленное** — это утечка по определению. Область
  отправки ограничена проектом и задачей: `.env`, ключи, бинарники, файлы вне
  проекта не уходят; состав отправки доступен пользователю.
- **Обновление не автоматическое.** Пока нет подписи релиза, апдейтер только
  показывает состав и diff, применяет по явному подтверждению и никогда не
  исполняет код из архива (zip-slip: пути нормализуются, выход за корень —
  отказ).
- **Fail closed.** Неизвестный инструмент, `kind`, хост, путь, версия — отказ.
  «На всякий случай разрешим» — дефект.
- **Проверка инструментом**: `python tools/security_audit.py` входит в
  `selfcheck` (R-18), атакующие тесты живут в `tests/py/security/`. Модуль с
  `effects != read` без этих тестов не получает `ported`.

**Почему так.** Агент — усилитель прав: у него запись в файлы, запуск Godot,
доступ к ключам и (в будущем) браузер с залогиненными сессиями. Его ошибка стоит
дороже ошибки обычного плагина: он либо сливает данные, либо становится чужим
инструментом на машине пользователя.

**Чего этот раздел не обещает.** Процесс под учёткой пользователя не защищён от
того, у кого уже есть доступ к этой учётке; провайдер видит отправленный код;
HTTPS без подписи не спасает от компрометации репозитория; браузерная ветка до
реализации — открытый риск, поэтому отложена (Q-08). Вместо обещания «вирусов не
будет» — проверяемое: агент не запускает чужой код и не пишет вне проекта.

**Как проверить нарушение.** `security_audit` красный; сетевой вызов вне
`substrate/llm`; секрет в файле плагина, в `reports/` или в корпусе; для нового
эффекта нет теста-атаки; подтверждение записи включается флагом из данных.

## R-21. Браузерная ветка не становится заметнее

**Формулировка.** Браузерная ветка работает на чужих площадках, где цена
заметности — бан аккаунта пользователя. Поэтому маскировка автоматизации **не
расширяется**: агент правит ровно то, что мешает рендеру, и только там, где это
доказано нужно. Улучшение в эту сторону запрещено: это не оптимизация, а риск.

**Как это выглядит на практике.**

- Разрешено ровно две подмены: `Document.prototype.visibilityState` → `'visible'`
  и `Document.prototype.hidden` → `false`, на прототипе (не на экземпляре
  `document`), с идемпотентной проверкой по дескриптору геттера.
- Запрещено добавлять: `navigator.webdriver`, `--disable-blink-features=AutomationControlled`,
  `excludeSwitches`, `useAutomationExtension`, подмену `document.hasFocus`
  (`toString()` выдаст себя), `window.chrome`, `navigator.plugins`, правку
  `toString` нативных функций.
- `needs_visibility_spoof` — флаг **сайта**, а не глобальный режим. У сайта,
  который читается из сети, он `false`, и `false → true` требует доказательства
  (без спуфа ответ не приходит) и записи в `docs/deviations.md`.
- Спуф не регистрируется «на всякий случай» на стартовой вкладке: `Page.addScriptToEvaluateOnNewDocument`
  живёт до закрытия вкладки и заражает все последующие сайты в ней.
- **Пользователь не должен страдать от работы агента, но и не должен ею
  пользоваться.** Chrome запускается в **отдельном профиле**
  (`%LOCALAPPDATA%\Godot_AI_Profile`), в своём окне, свёрнутом и без захвата
  фокуса (`STARTUPINFO` + `SW_SHOWMINNOACTIVE`); вкладки создаются и закрываются
  через CDP в своём окне. Обращение к профилю пользователя
  (`Google\Chrome\User Data`) запрещено: это и утечка его сессий, и невозможность
  на Chrome 136+ (там `--remote-debugging-port` требует нестандартного
  `--user-data-dir`). Данные — `contract/browser_stealth.json` → `profile`,
  `window_policy`, `forbidden_paths`.
- **Режим запуска закреплён.** Chrome запускается обычным процессом
  (`subprocess.Popen`) с `--remote-debugging-port=9222` и отдельным профилем;
  selenium работает только как клиент CDP через `debuggerAddress`. Запрещено:
  `webdriver.Chrome()` без `debuggerAddress`, `--enable-automation`, `--headless`.
  Именно этот режим держит `navigator.webdriver === false`; если браузером начнёт
  владеть selenium, chromedriver добавит `--enable-automation`, флаг станет `true`
  и защита площадки увидит агента сразу. Подменять `navigator.webdriver` в `false`
  тоже запрещено: подмена читается через дескриптор и `toString()` и хуже честного
  `false` (SEC-19, `contract/browser_stealth.json` → `launch`, `webdriver_flag`).
- Закреплённые значения — данные: `contract/browser_stealth.json`
  (`sites`, `launch`, `webdriver_flag`, `allowed_masking`, `forbidden_techniques`).
  Правка кода без правки контракта = нарушение.
- Если площадка перестала работать — решение ищется в другом месте (сеть,
  официальный API, отказ от площадки), а не усилением маскировки.

**Почему так.** Каждая новая подмена — это ещё одна строка, по которой страница
отличает управляемый браузер от обычного. При этом выгода нулевая: ответ либо уже
читается из сети, либо рендер и так придавлен флагами запуска Chrome. Плата за
«незаметность» — риск для пользователя, который не он выбирал.

**Как проверить нарушение.** `python tools/security_audit.py`: проверка SEC-20
падает при появлении запрещённой техники или при `true` у сайта, закреплённого с
`false`. Тест-страж: удаление строки из `forbidden_techniques` — тоже нарушение
(контракт худеет только решением, а не «чтобы тест прошёл»). Живая проверка:
сайт открывается, ответ приходит, `document.hasFocus.toString()` остаётся
нативным.

**Чего правило не обещает.** Что площадка не определит CDP-управление вообще:
определить можно, вопрос в том, что она считает поводом для бана. И оно не даёт
пользователю права нарушать правила площадки — раздел про технику, не про
разрешения.

## R-22. Устойчивость: регресс ловится кейсом, а не обещанием

**Формулировка.** Три вещи, без которых «мы ничего не сломали» — это надежда:

1. **Принятое поведение меняется только вместе с кейсом.** Правка общего кода
   (`python/kernel/`, `*/shared/`, `tools/`) без нового или изменённого кейса
   (`fixtures/corpus/…` или тест механики) не принимается: сначала красный кейс,
   потом код. Иначе корпус перестаёт быть замком поведения (R-09, R-16).
2. **Правило, на которое ссылается отчёт, должно ломаться мутацией.** Если правило
   нельзя нарушить так, чтобы проверка покраснела, — это не проверка, а долг:
   он пишется в `PROGRESS.md → Долги` с условием закрытия. Ссылаться в отчёте на
   инструмент, который этого не проверяет, запрещено (случай `lint_arch` и «в
   `domain/` нет IO», 2026-10-27).
3. **Доказательство снимается со сданного файла.** Мутация — только на той версии,
   что уходит в репозиторий; бэкап байтовый (`shutil.copyfile`), восстановление
   подтверждается `sha256` до/после, EOL файла сохраняется. Числа в отчёте берутся
   из вывода команды, итог `pytest` сверяется с суммой `--collect-only`.

**Почему так.** Архитектура даёт изоляцию (R-01, R-03, R-11), но не даёт гарантии
«старое не сломалось»: гарантию дают корпус, машинные проверки и то, что каждое
заявление подкреплено воспроизводимым выводом. Фазы 0–1 показали оба отказа сразу:
непокрытая защита в `_type_ok` и отчёт, доказывавший мутацию не того файла.

## Целевая раскладка внутри папки плагина

Раскладка — следствие R-01, а не отдельное правило: ничего не выносится
наружу, поэтому всё перечисленное живёт под `addons/godot_agent/`.

Все пути в этом файле даны от корня проекта. Запись `python/modules/...`
означает `addons/godot_agent/python/modules/...`: папки `python` в корне проекта
нет и быть не должно.

```
addons/godot_agent/
├─ plugin.cfg                 # манифест плагина
├─ plugin.gd                  # вход: включение/выключение, запуск backend-процесса
├─ RULES.md                   # этот файл
├─ AGENTS.md                  # что ИИ-агент обязан прочитать и чего не делает
├─ editor/                    # GDScript: всё, что работает внутри редактора
│  ├─ core/                   # жизненный цикл плагина, состояние, конфиг, лог
│  ├─ bridge/                 # сокет, диспетчер, примитивы редактора (руки, не голова)
│  ├─ ui/                      # панель агента, виджеты, тема
│  ├─ harness/                # headless-прогон: manifest -> load -> result.json
│  └─ settings/
├─ runtime/                    # игровая половина: проба в запущенной игре, отчёт
├─ icons/
├─ python/                    # Python-часть
│  ├─ kernel/                 # универсальные типы: ошибки, diff, пути, ToolSpec, WritePlan, лимиты
│  ├─ formats/                # разбор .gd и .tscn: без IO и без Godot
│  ├─ runtime/                # bootstrap, профили, загрузчик модулей, health, лог
│  ├─ substrate/              # реализации портов: fs, editor, engine, store, llm
│  ├─ modules/                # ВСЕ фичи: модуль = папка (R-02)
│  ├─ protocol/               # сборка реестра, генерация схем, маппинг ошибок
│  └─ channels/               # mcp/, http/, cli/ — тонкие ветки (R-04)
├─ contract/                  # схемы протокола — единственный источник правды
├─ tests/                     # кросс-модульные тесты и e2e (тесты фичи — в её папке)
├─ docs/                      # архитектура, паритет, прогресс, листы механик, ADR
├─ tools/                     # probe, selfcheck, snapshot_record, линтер границ, лимиты, сборка
└─ pyproject.toml             # конфиг Python-части
```

Про `.gdignore`: он не используется. Godot не импортирует `.py` (для них нет
импортёра), поэтому Python-часть спокойно живёт внутри папки плагина и просто
видна в доке файловой системы редактора. Прятать её незачем: всё агентское
должно быть на виду и внутри своей папки. Если однажды шум в доке станет
проблемой, это решается отдельным решением, а не выносом файлов наружу.

## Открытые вопросы

Решения по ним ещё нет, поэтому это не правила.

- **Q-01. Рантайм-состояние.** Журнал правок и кэш Godot API — где им жить:
  `user://godot_agent/` (вне репозитория, но и вне папки плагина) или внутри
  папки плагина. R-01 говорит про исходники и поставку, а не про данные,
  возникающие при работе; нужно явно закрепить выбор, пока он не решился сам.
- **Q-02. Python внутрь аддона.** Бандлить интерпретатор, требовать системный
  Python или ставить окружение при первом включении плагина.
- **Q-03. Имя плагина и порт.** Совпадают ли они со старым агентом (тогда в
  одном проекте одновременно не включатся) или разведены.
- **Q-04. Способ регистрации модуля.** R-03 исходит из автообнаружения
  (правок вне папки модуля — ноль). Альтернатива, прозвучавшая в обсуждении:
  явный список модулей в главном файле (1–2 строки). Второй вариант нагляднее,
  но удаление папки без правки списка ломает старт, то есть противоречит
  R-03. Решение нужно принять до первого модуля.
- **Q-05. Где хранятся снапшоты.** В репозитории (R-07 требует диффов в ревью,
  но объём растёт: текстовые ответы на большой корпус могут весить десятки
  мегабайт) или отдельным артефактом CI (легко, но эталон не виден в ревью).
  Возможен компромисс: в репозитории — корпус входов и хеши/сжатые эталоны
  ответов, полные снапшоты — артефактом.
