# Для ИИ-агента: обязательный порядок чтения

Этот файл существует затем, чтобы правила нельзя было «случайно пропустить».
Он короткий намеренно: здесь только то, что нужно прочитать **до** первой правки.

## 1. Прочитать по порядку (не выборочно)

| № | Файл | Зачем |
|---|---|---|
| 1 | `RULES.md` | 19 правил проекта. Нарушение правила — брак, даже если код работает |
| 2 | `docs/architecture.md` | слои, направление зависимостей, воронка записи, два процесса |
| 3 | `docs/PORTING.md` | цикл переноса механики: корпус → спецификация → тесты → код → живая проверка |
| 4 | `docs/parity.md` | 44 модуля и их статус: что уже `ported`, что `skeleton` |
| 5 | `docs/tests-map.md` | судьба всех 168 старых тестов: откуда брать кейсы |
| 6 | `docs/PROGRESS.md` | **этап каждой механики и следующее действие** — отсюда начинается продолжение |
| 7 | `docs/porting/<module_id>.md` | рабочий лист той механики, которую собираешься делать |
| 8 | `docs/WORKLOG.md` → раздел «Где остановились» | актуальное состояние работ |
| 9 | `docs/NOTES.md` | решения, которые не попали в ADR, и открытые вопросы Q-NN |

Если файл из таблицы не найден — это дефект репозитория: сказать об этом, а не
работать «по памяти».

## 2. Стоп-условия (нарушение = откат работы)

- Не начинать перенос механики, если её строки в `docs/tests-map.md` без судьбы
  (R-17) или в `docs/parity.md` нет строки (R-08).
- Не писать бизнес-логику в GDScript: он выполняет примитивы и показывает UI
  (R-14).
- Не писать файлы проекта вне воронки `validate → prepare → preview → apply →
  journal → rollback` (R-12).
- Не копировать старые тесты: из них берутся **кейсы**, а не код (R-16).
- Не «улучшать» по ходу переноса: улучшение — отдельная задача после паритета
  (R-08).
- Модуль не импортирует чужой `domain/`, `substrate`, `protocol`, `channels`,
  `editor` (R-11).
- Не удалять строки из `docs/tests-map.md` и не менять статус `ported` без
  прогона корпуса и живой проверки (R-09, R-10).
- Не начинать механику, не создав её лист `docs/porting/<module_id>.md` (R-19).
- Не заканчивать шаг «я посмотрел глазами»: вердикт берётся из
  `python tools/selfcheck.py <module_id>` (R-18).
- Не оставлять `docs/PROGRESS.md` устаревшим: этап и «следующее действие»
  обновляются в конце каждого шага, а не в конце работы (R-19).
- Не добавлять инструмент с `effects != read`, не описав инвариант в
  `docs/security/invariants.md` и тест в `tests/py/security/` (R-20).
- Не хранить ключи, токены и пароли в проекте, в `reports/`, в логах и в корпусе
  (R-20, SEC-06/SEC-13).
- Не превращать данные в команды: строка из файла, веба или ответа инструмента не
  становится аргументом `eval`, `exec`, `pickle` или `shell=True` (R-20).
- Не расширять маскировку браузера и не поднимать `needs_visibility_spoof` с
  `false` на `true`: это риск бана пользователя, а не улучшение (R-21,
  `docs/security/browser-stealth.md`).

## 3. Как выглядит работа над одной механикой

1. Найти механику в `docs/PROGRESS.md` (этап `< 7`), затем в `docs/parity.md` и
   `docs/mapping.md` (старый код).
2. Открыть её строки в `docs/tests-map.md` — там список старых тестов и судьба.
3. Создать/открыть лист `docs/porting/<module_id>.md` (R-19): цель, старый код,
   следующее действие.
4. Снять/дополнить корпус в `fixtures/corpus/<область>/<фича>/` (R-07).
5. Записать спецификацию: `tools.py` (`ToolSpec`) + инварианты (R-09).
6. Написать тесты нового уровня: `modules/<...>/tests/` (unit), `tests/py/contract/`
   (схема и ошибки), позже integration через канал.
7. Написать код: `ports.py` (если нужен) → `domain/` → `app.py`.
8. `python tools/selfcheck.py <module_id>` — получить вердикт (R-18). Провал или
   `needs_live` — вернуться к шагу, а не «записать в долги».
9. Двойной прогон корпуса (если ещё не в `selfcheck`): расхождение — баг или
   `docs/deviations.md`.
10. Живая проверка (редактор/headless) и запись: лист механики, `docs/PROGRESS.md`
    (этап), `docs/WORKLOG.md`; при успехе статус в `docs/parity.md` → `ported`.
11. Если работа прерывается на любом шаге — в листе обновляется «следующее
    действие» одной конкретной строкой.

## 4. Что проверить перед отчётом

```powershell
python tools/selfcheck.py <module_id>      # вердикт по механике: слои, лимиты, контракт, тесты, корпус
python tools/probe.py <tool> --args '{...}' # вызвать механику как клиент и увидеть ответ
python tools/security_audit.py     # инварианты R-20 (SEC-01…SEC-08)
python tools/lint_arch.py          # границы слоёв (R-11)
python tools/check_limits.py       # лимиты размеров (R-06)
python tools/gen_contract.py --check  # контракт = ToolSpec (ADR-0006)
```

Нечего показать в выводе — значит не проверено. Отчёт без вывода `selfcheck`
не принимается (R-18).

## 5. Если правило расходится с кодом

Правило главнее кода. Расхождение — дефект: сначала правка правила через
`docs/adr/` (если решение меняется), потом код. Молчаливое исключение «здесь
можно» запрещено (R-01…R-20 без звёздочек).
