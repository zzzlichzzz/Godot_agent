# MCP Alpha — план исправлений по результатам аудита

Документ для передачи в отдельные чаты. Каждый этап самодостаточен: его можно
отдать одному чату целиком. Этапы 1–4 независимы друг от друга и могут идти
параллельно. Этапы 5–6 выполняются после них. Повторный аудит — после того,
как все этапы закрыты.

Исходники: `python/tools/agent_bridge.py` (~1250 строк), `python/tools/MCP_ALPHA.md`,
тесты `python/tests/test_agent_bridge.py` (43 теста, все зелёные на момент
аудита), `python/tests/test_gdscript_wiring.py` (109 проверок).

Общие правила для всех этапов:

- кодировка UTF-8, русские docstring/комментарии в стиле файла;
- точечные правки, без рефакторинга соседнего кода;
- на каждый этап добавить тесты в `test_agent_bridge.py`; для правок в
  `agent_panel.gd` — проверку в `test_gdscript_wiring.py` и поднять
  `EXPECTED_CHECK_COUNT`;
- перед сдачей этапа прогнать из каталога `python`:
  `python tests/test_agent_bridge.py` (ожидается 43 + N новых тестов, 0 failed)
  и `python tests/test_gdscript_wiring.py`, если затронут wiring/панель;
- обновить `MCP_ALPHA.md`, если меняется наблюдаемое поведение или контракт;
- каждый этап завершать коммитом вида `fix(mcp-alpha): <что исправлено>`.

Ниже все ссылки на строки даны по состоянию файла на момент аудита.

## Этап 1. `check` не должен врать о недоступной валидации Godot

Приоритет: критический. Файлы: `agent_bridge.py`, `MCP_ALPHA.md`, тесты.

Проблема. `_check_one_path` вызывает
`godot_headless_validation.validate_batch(...)` и кладёт `report` в
`result["headless"]`, но `cmd_check` (стр. 630–637) читает только
`report["new_diagnostics"]` и полностью игнорирует `report["blocking"]`,
`report["status"]` и `report["mode"]`. Воспроизведено: валидный `.gd` с
`--validation required` при отсутствующем Godot вернул `rc=0` и
«1 files clean», тогда как `write apply` на тех же условиях отказал с
«обязательная проверка настоящим Godot недоступна: executable не найден».
В выводе `check` нет ни слова о headless-статусе.

Что сделать.

1. В `_check_one_path` пробрасывать признак блокировки наверх: при
   `report.get("blocking")` добавлять в `result["problems"]` явную строку
   о недоступной/блокирующей headless-проверке, используя
   `godot_headless_validation.blocking_message(receipt)` как источник
   формулировки, чтобы тексты не расходились с `write apply`.
2. Печатать в `cmd_check` для каждого пути строку `headless: <status>`
   (`passed` / `failed` / `inconclusive` / `unavailable` / `skipped`),
   чтобы вывод не был двусмысленным при отсутствии Godot.
3. Считать блокировку инфраструктурным сбоем, а не «not-found»: если
   `blocking` вызван `status == "unavailable"`, возвращать `RC_ERROR`
   («инструмент НЕ СМОГ ответить» по контракту), а не `RC_NOT_FOUND`.
4. Не трогать `--validation off` и `auto`: там `blocking` не выставляется,
   поведение остаётся прежним.

Тесты (класс `AgentBridgeTests` в `test_agent_bridge.py`).

- `check` на валидном `.gd` с `--validation required` и
  `--godot <несуществующий путь>` возвращает не `0`, и в stdout есть
  `headless: unavailable`;
- тот же случай с `--validation off` возвращает `0` и `headless: skipped`;
- блокирующая headless-проверка попадает в `problems`, а не теряется;
- причина блокировки не маскируется под «not-found»: код возврата не `2`.

Документация. В `MCP_ALPHA.md` (раздел «Режимы доступа», стр. 36–40) явно
написать: `--validation required` влияет и на `check` — без настоящего Godot
проверка не может считаться выполненной, и мост сообщает об этом, а не
сообщает «clean».

## Этап 3. Убрать зависимость `plan_id` от рабочей директории

Приоритет: высокий. Файлы: `agent_bridge.py`, тесты. Правка мала, но
обязательна — она ломает базовый сценарий preview/apply.

Проблема. `_plan_digest` (стр. 715–728) вычисляет
`"addon_dir": os.path.normcase(os.path.realpath(policy.get("addon_dir") or ""))`.
При `addon_dir is None` (режим `--access project`) вызывается
`os.path.realpath("")`, а он возвращает текущий рабочий каталог. Итог: один
и тот же запрос из разных папок даёт разные `plan_id`. Воспроизведено —
`9685adfd…` из каталога A и `2d02c176…` из каталога B; preview в A с
последующим apply в B падал с «stale plan; request, access mode, or source
changed», хотя запрос, режим и исходник не менялись. В режиме `addon` с
найденным агентом эффект не проявлялся.

Что сделать.

1. Нормализовать `None` в пустую строку ДО вызова `realpath`, чтобы `None`
   давал стабильный `""`: взять `raw = policy.get("addon_dir") or ""` и
   применять `os.path.normcase(os.path.realpath(raw))` только при непустом
   `raw`, иначе оставлять `""`.
2. Не вводить других зависимостей от окружения в digest.

Тесты (создать две разные временные директории, запускать `main` с разным cwd).

- один и тот же request в режиме `project` даёт одинаковый `plan_id` из
  разных cwd;
- preview из A + apply из B с тем же `plan_id` проходит (в режиме `off`,
  чтобы не зависеть от наличия Godot), файл реально изменён;
- существующая защита «план одноразовый» продолжает работать: повторный
  apply с тем же `plan_id` отклоняется.

## Этап 4. Честный отчёт `check` о непроверяемых файлах

Приоритет: высокий. Файлы: `agent_bridge.py`, `MCP_ALPHA.md`, тесты.

Проблема. В `_check_one_path` ветки проверки существуют только для `.gd`,
`.tscn`, `.py`, `.json`, `.cfg`. Для `.md`, `.png` и `project.godot` не
выполняется ни линтер, ни headless-валидация, но `cmd_check` выводит
«N files clean» и `rc=0`. Воспроизведено для `res://notes.md`,
`res://img.png`, `res://project.godot`. Модель принимает это за проверку.

Что сделать.

1. Ввести явное состояние по каждому пути: `checked: true|false` с
   причиной при `false` («расширение не проверяется этим каналом»).
2. Итоговую строку строить по фактически проверенным файлам: если проверено
   `k` из `n`, выводить `checked: k/n`, и при `k == 0` не заявлять «clean».
3. Не расширять набор расширений в этом этапе (это отдельное решение) —
   только сделать отчёт честным.

Тесты.

- `check` на `.md`/`.png` не сообщает «clean» и показывает `checked: false`;
- смешанный вызов (`.gd` + `.png`) даёт `checked: 1/2`;
- поведение для полностью проверенного набора не меняется.

   headless-слоя уже считается по файлу целиком (стр. 604), его не трогать.

## Этап 5. Согласовать коды возврата и режимы доступа

Приоритет: средний. Файлы: `agent_bridge.py`, `MCP_ALPHA.md`, тесты.
Может потребовать предварительного решения: что считать «инструмент не смог».

Проблема 5a — контракт кодов. `MCP_ALPHA.md:96` требует проверять код после
каждого вызова и определяет `3` как «инструмент НЕ СМОГ ответить», однако
для инфраструктурных отказов возвращается `2` («not-found»): недоступный
`required`-Godot, отсутствующая квитанция плана, несуществующий journal
entry, а также `ValueError` из разбора опций и `_read_request`. Наружу
уходит, например, «refused: plan already applied, in progress, unknown, or
expired», что по контракту читается как «объект не найден».

Проблема 5b — usage-семантика. `_json_request_option` и `_parse_write_options`
рассчитаны на отказ с кодом `4`, но `cmd_write`/`cmd_context` гасят
`ValueError` до `RC_NOT_FOUND`: неверный `--plan-id` и отсутствующий
`--request` дают `2` вместо `4`.

Проблема 5c — молчаливая деградация режима. `_access_policy` (стр. 191–194)
при недоступном доверенном корне для `addon` молча возвращает
`allow_addons: False`; режим, заявленный как «обычные файлы + внешние
аддоны», деградирует до project без предупреждения, и `status`/`engine`
это не отражают.

Проблема 5d — фильтр защищённых путей покрывает не все ветки.
`_validate_bridge_candidate` вызывается только для транзакций. Для
`repair_scene` (`.tscn`) и `rename_symbol` путь до `dist/`, `__pycache__`,
`parser_corpus` при `allow_self_edit` проходит, и единственная защита —
конкатенация `os.path.join(project_root, candidate[6:])` в
`_assert_prepared_access` (стр. 751), которая не канонизирует путь и не
защищает от уже существующей симлинковой ссылки внутри `addons/`.

Проблема 5e — мелочь. `cmd_search` (стр. 430–443) не отвергает повтор
`--max` (в отличие от `_parse_write_options`, где дубликат отвергается).

Что сделать.

1. Развести отказы: инфраструктурные (недоступный Godot, битая квитанция,
   отсутствующая journal-запись) — `RC_ERROR` с внятным текстом;
   «объекта нет / отказ политики по существу» — оставить `RC_NOT_FOUND`.
2. Ошибки разбора опций и запроса отдавать как `RC_USAGE` (4), а не гасить
   в `2`. `main()` уже валидирует `--access` и `--validation` именно так
   (стр. 1236–1240) — привести остальные пути к тому же поведению.
3. В режиме `addon` при недоступном доверенном корне печатать явное
   предупреждение о деградации, а не работать молча.
4. Вынести фильтр `PROTECTED_AGENT_PARTS` в общий для всех write-веток
   путь вместо только транзакций; использовать каноническое разрешение
   пути вместо `os.path.join` с ручным срезом префикса.
5. Отвергать повтор `--max` в `cmd_search` кодом `4`.
6. Обновить таблицу кодов и раздел «ЖЁСТКИЕ ПРАВИЛА» в `MCP_ALPHA.md`,
   чтобы модель знала, что 3 = «мост не смог», и не искала причину
   в несуществующем объекте.

Тесты.

- недоступный `required`-Godot даёт не `2`;
- неверный `--plan-id` и отсутствующий `--request` дают `4`;
- `repair_scene`/`rename_symbol` в `res://.../dist/...` при `agent-dev`
  отклоняются;
- повтор `--max` в `search` даёт `4`;
- предупреждение о деградации режима присутствует в выводе.

## Этап 6. Уборка осиротевших квитанций планов (по желанию)

Приоритет: низкий. Файлы: `agent_bridge.py`, `MCP_ALPHA.md`, тесты.

Проблема. `_claim_plan_receipt` переименовывает файл в
`<plan>.applying-<pid>`; при падении процесса он остаётся навсегда и
блокирует повторный apply с этим `plan_id`, а сборки старых квитанций по
TTL нет, поэтому каталог `bridge_plans` растёт монотонно.

Что сделать. Добавить best-effort очистку: удалять `.json`-квитанции старше
`PLAN_TTL_SECONDS` и осиротевшие `.applying-*`, вызывая перед записью новой
квитанции в `cmd_write` (preview) и в `_claim_plan_receipt`. Сборку сделать
устойчивой к `OSError` и не трогать файлы активного `apply` текущего
процесса. Описать в `MCP_ALPHA.md`, что падение процесса во время apply
оставляет пометку `.applying-<pid>` и что делать оператору.

Тесты.

- просроченная квитанция удаляется при следующем preview;
- `.applying-<pid>` текущего процесса не удаляется;
- очистка не бросает исключений при отсутствии каталога.

## Порядок и приёмка

Рекомендуемый порядок: этапы 1, 2, 3 и 4 независимы — их можно раздать
четырём разным чатам одновременно. Этап 5 зависит только от понимания
контракта и может идти параллельно с 1–4, но не должен пересекаться с ними
по строкам `cmd_check`/`_check_one_path` — согласовывать правки, чтобы не
затереть друг друга. Этап 6 делается последним и только по желанию.

После закрытия этапов выполняется повторный аудит по тем же методикам
(живые пробы на временном проекте, сверка с `MCP_ALPHA.md`, прогон
`test_agent_bridge.py` и `test_gdscript_wiring.py`). Критерии приёмки
аудита: ни один из воспроизведённых сценариев больше не даёт ложный успех;
коды возврата соответствуют документированному контракту; `plan_id` стабилен
относительно окружения; защищённые пути недоступны во всех write-ветках.


Тесты.

- большой `.gd` с дефектом за пределами окна `max_chars` больше не
  возвращает «clean»;
- дефект до окна по-прежнему находится (защита от регрессии);
- в выводе явно присутствует признак частичной проверки.
