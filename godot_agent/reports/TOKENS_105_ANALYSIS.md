## 2. Пять причин (от большей к меньшей)

1. **Мёртвый сторож + мёртвый фильтр волны = волна 1 стояла 63 минуты, а волны 2–4
   закрывались мгновенно по старым строкам.** По фактам 74 прогонов «Агрегатора каналов»:
   `agg_polls` был равен **1 во всех 74 прогонах** (инкремент не переживал wait-паузы —
   static data теряла запись), поэтому cap=75 не срабатывал никогда; `wave_start_ms`
   терялся так же, поэтому каждая волна, закрываясь, видела отчёты прошлых волн
   (`done=true` на первом же опросе: прогоны 72–73). Итог: каналы 4 раза получали
   ОДНУ И ТУ ЖЕ задачу и 4 раза проходили стадии 1–5 — это и есть основной объём
   (~28–35M из ~50M).
2. **Зацикливание стадии «3. Фикс» у API и MCP.** Узел — агент с `maxIterations=24`
   и `retryOnFail=True (maxTries=2)`: при упорном отказе инструментов (у MCP — ошибки
   путей `res:\…`, вызовы `functions` без обязательного `path`) агент добивал 24
   итерации, затем нода перезапускала ВЕСЬ цикл ещё одну полную попытку (maxTries=2 = две попытки всего) = до 48 вызовов агента
   на один прогон; каждый вызов ~30–56K prompt → до ~1.5–2.7M токенов на один застрявший
   прогон. Именно так «сбой» превращался в пожирателя токенов.
3. **Дорогие контексты шагов.** Средний вызов агента ~30K, максимум 55–56K (API/Браузер):
   каждый шаг агентского цикла заново отправляет историю с выводами инструментов.
   Субагент-Поисковик — 21–35K на вызов (133 вызова только у Редактора).
4. **Аудитор в ядре — 197 вызовов за круг** (~6.1M) против 7 вызовов у Планировщика:
   после каждого мгновенно-закрытого круга он заново «изучал» проект и строил планы.
5. **55 минут «мёртвой зоны» 13:55→14:49**: каналы волны 1 уже завершились (успех/сбои),
   шина их не видела (нет строк), сторож молчал — цикл был в простое, после чего
   оркестратору пришлось вручную дописать строки отчётов в таблицу «Шина каналов».

## 3. Что теперь исправлено (13.10.2026)

| Дефект | Исправление | Ожидаемый эффект |
|---|---|---|
| static data не переживает wait; волны путались | `wave_start_ms` живёт в пакете волны (execution data) — его читает агрегатор `$('Шина: стартовый пакет').last()`; добавлен фильтр свежести строк 45 мин | волна видит только свои отчёты; мгновенных ложных закрытий нет |
| сторож-счётчик не существовал | таймаут по времени: `CAP_MIN=30` от метки волны | зависшая волна закрывается за ≤30 мин с пометкой, а не «никогда» |
| сбои каналов «не видны» | Error Trigger в воркфлоу: упавший канал сам пишет строку `status=failed` + дзынь в шину | ошибка сообщается В МОМЕНТ возникновения; волна не ждёт молча |
| NULL-строки отчётов | узел «X: отчёт-сбор (код)» собирает status/summary с try/catch до записи в таблицу | отчёт всегда читаемый; не «пустышка» |
| дзынь-404 (редкие) | дзынь читает resume-URL ещё и из body триггера (fallback) | меньше потерянных пробуждений; 60-сек поллинг остаётся страховкой |
| retryOnFail у «3. Фикс» | снят (вторая попытка 24-итерационного цикла — до 48 вызовов — больше не запускается) | ≈ −50% токенов на застрявшей стадии |

## 4. Рекомендации (не в этой задаче)

- `maxIterations` стадий «3. Фикс»/«4. Прогон тестов»: 24 → 16 (быстрее честный провал).
- Схемы/описания инструментов MCP «руки» (`:8010`) и «инструменты Godot» (`:8000`):
  сделать `path` обязательным и описать ошибку путём научающе — агент перестанет
  молотить одно и то же.
- Память агентов: обрезать историю шагов (сейчас весь журнал инструментов летит в каждый вызов).
- Ринг-лимит ядра (`Счётчик кругов`, static) — та же болезнь, что у `bus_polls`;
  перевести на число прогонов «Сборщика» в исполнении — отдельной задачей.
- Таблица «Шина каналов» растёт (~16–20 строк/цикл); раз в N циклов чистить по `run_id`.
