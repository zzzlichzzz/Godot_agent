# Дорожная карта глубокой интеграции с Godot

Фактически реализованный объём, ограничения, настройка runtime bridge и
актуальный набор проверок зафиксированы в
[`GODOT_INTEGRATION_STATUS.md`](GODOT_INTEGRATION_STATUS.md).

## Цель

Развить браузерную часть агента так, чтобы большая часть разведки, проверки и исполнения выполнялась локально средствами Godot, а нейросеть использовалась для принятия смысловых решений.

Целевой сценарий:

1. Godot локально собирает небольшой релевантный контекст задачи.
2. Агент отправляет модели один запрос.
3. Модель возвращает пакет высокоуровневых структурированных действий и проверок.
4. Локальный исполнитель проверяет пакет, показывает пользователю изменения и применяет их после подтверждения.
5. Godot запускает линтеры и настоящую проверку движком.
6. Повторный запрос к модели выполняется только при ошибке, которую нельзя исправить детерминированно.

Основной критерий развития браузерного режима: минимизировать не локальные вычисления, а количество обращений к нейросети и число токенов, передаваемых между обращениями.

## Принятые архитектурные решения

- Текущий адресный откат по кнопке и журнал изменений сохраняются как основной механизм восстановления.
- Общий `EditorUndoRedoManager` не используется для действий агента. История пользователя и история агента не должны случайно отменять изменения друг друга.
- Существующие `gd_lint`, `gd_api_check` и `tscn_lint` сохраняются. Проверка настоящим Godot дополняет их, а не заменяет.
- Контекст живого редактора передаётся по бюджету и только когда он относится к запросу. Полный снимок сцены или Inspector не добавляется в каждый промпт.
- Структурные команды предпочтительнее генерации текстового `.tscn`, `.tres` или `project.godot`, если действие можно безопасно выразить через API Godot.
- Все пакетные изменения сначала проверяются как единая транзакция и применяются только после подтверждения пользователя.
- Существующие текстовые операции остаются запасным путём для случаев, которые ещё не покрыты структурным исполнителем.

## Бюджет контекста

Текущий стартовый промпт занимает примерно 4000 токенов. Контекст редактора не должен бесконтрольно увеличивать постоянный системный промпт.

Предлагаемые правила:

- Постоянный системный промпт содержит только протокол, возможности агента и стабильную краткую карту проекта.
- Динамический контекст редактора отправляется отдельным блоком пользовательского хода.
- Ориентир для автоматического контекста: 800–1500 токенов в обычной задаче.
- Жёсткий первоначальный предел: 2500 токенов динамического контекста без явного запроса модели на дополнительные данные.
- В контекст попадает выделенный фрагмент или текущая функция, а не весь открытый скрипт.
- Для выбранных узлов передаются только изменённые, скриптовые и часто используемые свойства, а не весь `get_property_list()` со значениями.
- Большая сцена передаётся как путь выбранного узла, его ближайшее окружение и связанные скрипты, а не полное дерево.
- Несохранённый буфер передаётся как diff относительно диска, если это короче полного текста.
- Каждый раздел снабжается локальной оценкой размера и отбрасывается по приоритету при превышении бюджета.
- Фактический размер контекста и число предотвращённых дополнительных запросов следует записывать в локальную телеметрию.

Приоритеты усечения: диагностика и выделение сохраняются первыми; затем текущая функция, выбранные узлы и зависимости; обзор проекта и длинные списки свойств удаляются первыми.

## Этап 1. Контекст живого редактора

Добавить формирование `EditorContextSnapshot` в GDScript-плагине и отправлять его серверу вместе с сообщением пользователя.

Снимок может содержать:

- активную и открытые сцены;
- текущий скрипт, функцию, позицию курсора и выделение;
- несохранённые изменения текущего `CodeEdit`;
- выбранные через `EditorInterface.get_selection()` узлы и ресурсы;
- пути, типы, группы, владельцев и подключённые скрипты выбранных узлов;
- небольшой белый список релевантных свойств Inspector;
- состояние запуска проекта и последнюю агрегированную диагностику.

Требования:

- сбор снимка не должен изменять проект;
- сериализация должна иметь версию схемы;
- пустые разделы не отправляются;
- пользовательский текст остаётся главным сигналом, снимок не должен подменять намерение пользователя;
- сервер должен логировать только размеры разделов, не дублируя содержимое пользовательского проекта в диагностический журнал без необходимости.

Критерий готовности: запросы вида «измени выбранного врага» и «исправь эту функцию» выполняются без предварительных `list_scene` и `read_file`, если нужный объект уже открыт в редакторе.

## Этап 2. Составной сборщик контекста

Добавить read-only действие `gather_context`, объединяющее существующие локальные возможности:

```json
{
  "action": "gather_context",
  "active_scene": true,
  "selection": true,
  "symbols": ["Player.take_damage", "Enemy.attack"],
  "dependencies": true,
  "diagnostics": true,
  "godot_api": ["CharacterBody2D", "AnimationPlayer"],
  "max_chars": 12000
}
```

Один локальный проход должен уметь вернуть:

- выбранные функции и объявления;
- связанные сцены и ресурсы;
- callers и наследников;
- подключения сигналов;
- autoload и InputMap, относящиеся к задаче;
- методы и свойства ClassDB;
- ошибки и предупреждения по затронутым файлам.

Сборщик не заменяет `read_file`, `read_function`, `list_scene` и Библиотекаря: они остаются точечными инструментами и внутренними источниками составного ответа.

Критерий готовности: типовая разведка, ранее требовавшая нескольких последовательных действий модели, возвращается одним компактным ответом с указанием источников.

## Этап 3. Безопасный рефакторинг символов, узлов и ключей

Реализовать локальный рефакторинг по аналогии с IDE: переименование объявления автоматически обновляет только его реальные использования во всём проекте.

Необходимо разделять разные виды имён:

- классы `class_name`;
- функции и их вызовы;
- сигналы и подключения;
- свойства, поля, константы и enum;
- пути и имена узлов;
- группы;
- InputMap actions;
- ключи словарей и `StringName`;
- пути ресурсов, `preload()` и `load()`;
- ссылки в `.gd`, `.tscn`, `.tres` и `project.godot`.

Базовая команда:

```json
{
  "action": "rename_symbol",
  "kind": "signal",
  "declaration": "res://enemies/monster.gd:12",
  "old_name": "health_changed",
  "new_name": "hp_changed"
}
```

Правила безопасности:

- Нельзя выполнять слепую глобальную замену текста.
- Сначала строится список объявлений и ссылок с типом и уверенностью.
- Строки и комментарии не меняются, кроме подтверждённых строковых ссылок Godot, например signal name, `NodePath`, group или InputMap action.
- Локальные переменные с одинаковым именем в других областях видимости не затрагиваются.
- Динамические вызовы `call()`, `get()`, `set()`, строковые ключи и вычисляемые `NodePath` помечаются как неоднозначные.
- Неоднозначные совпадения показываются отдельно и по умолчанию не изменяются автоматически.
- Перед применением показывается единый preview всех файлов.
- После применения запускаются индексирование, линтеры и проверка Godot.
- Весь рефакторинг записывается одной цепочкой в существующий журнал и откатывается одной кнопкой.

Начальный порядок реализации:

1. Переименование `class_name`, функций, сигналов и статически известных вызовов в `.gd`.
2. Переименование путей ресурсов с обновлением ссылок и UID.
3. Переименование узлов и статических `NodePath` в сценах и скриптах.
4. Переименование групп и InputMap actions.
5. Переименование строковых ключей словарей только при доказуемой связи с выбранным объявлением или после явного подтверждения списка совпадений.

Критерий готовности: переименование сигнала или функции обновляет объявление, статические вызовы, подключения сцен и связанные ссылки, не затрагивая одноимённые сущности в другой области видимости.

## Этап 4. Структурное редактирование сцен

Добавить высокоуровневые действия:

```json
{"action":"add_node","scene":"res://player/player.tscn","parent":"Player","type":"Timer","name":"CoyoteTimer"}
{"action":"set_node_property","scene":"res://player/player.tscn","node":"Player/Sprite2D","property":"flip_h","value":true}
{"action":"connect_signal","scene":"res://player/player.tscn","from":"Player/Timer","signal":"timeout","to":"Player","method":"_on_timeout"}
{"action":"attach_script","scene":"res://player/player.tscn","node":"Player/Health","path":"res://player/health.gd"}
{"action":"reparent_node","scene":"res://player/player.tscn","node":"Player/Weapon","new_parent":"Player/Hand"}
```

Исполнитель должен использовать `PackedScene`, `ResourceLoader`, `ResourceSaver` и корректно управлять `Node.owner`. Для открытой изменённой сцены необходимо учитывать несохранённое состояние и не перезаписывать его версией с диска.

Требования безопасности:

- перед сохранением проверять уникальность путей узлов и совместимость типа свойства;
- сохранять исходный снимок в текущем журнале отката;
- загружать сохранённую сцену повторно до фиксации успешного результата;
- не использовать общий Undo/Redo редактора;
- при невозможности безопасной структурной операции отказываться от применения, а не переходить молча к текстовой перезаписи.

Критерий готовности: слабая модель может создать и связать небольшую сцену коротким набором команд без генерации сырого `.tscn`.

## Этап 5. Настройки проекта через API

Добавить структурные команды:

- `add_input_action` и `add_input_event`;
- `set_project_setting`;
- `add_autoload` и `remove_autoload`;
- `set_main_scene`;
- `set_layer_name`;
- `set_display_settings`.

Использовать `ProjectSettings`, `InputMap` и методы `EditorPlugin` вместо текстовой правки `project.godot`.

Это направление оправдано не количеством строк, а надёжностью: модель выбирает намерение и значения, а Godot отвечает за сериализацию, типы и актуальный формат файла. Команды следует добавлять по мере реальных сценариев, не создавая заранее универсальную обёртку над всеми настройками.

Критерий готовности: добавление действия ввода или autoload не требует от модели читать и переписывать `project.godot`.

## Этап 6. Многоуровневая диагностика

Сохранить текущие быстрые проверки до применения:

1. `gd_lint` для дешёвых и понятных ошибок GDScript.
2. `gd_api_check` для сверки с ClassDB конкретной версии Godot.
3. `tscn_lint` для защиты структуры сцен.
4. Анализ зависимостей сцена-скрипт.

После них добавить настоящую проверку движком:

- проверка кандидата в контексте копии или overlay проекта;
- загрузка затронутых скриптов, сцен и ресурсов;
- структурированный разбор файла, строки, столбца, категории и текста ошибки;
- таймаут и корректное завершение headless-процесса;
- отделение новых ошибок кандидата от уже существовавших ошибок проекта.

Линтеры должны останавливать заведомо опасное изменение до запуска более дорогой проверки Godot. Успешная regex-проверка никогда не считается заменой загрузке движком.

Критерий готовности: невалидный GDScript или сцена не попадают в проект, а модель при необходимости получает один агрегированный отчёт вместо последовательности ошибок.

## Этап 7. Семантический индекс проекта

Развить текущий индекс в инкрементальный граф:

- объявления и использования символов;
- наследование;
- сцены, скрипты и ресурсы;
- callers;
- сигналы и подключения;
- группы, autoload и InputMap;
- `NodePath`, UID и пути ресурсов;
- зависимости импорта;
- отметка `mtime + size + hash` для повторного использования данных.

Добавить IDF-взвешивание и контентный кэш `.gd`, уже описанные в `ОТЛОЖЕНО.md`. Индекс должен обслуживать Библиотекаря, `gather_context`, безопасный рефакторинг и оценку влияния транзакции, а не создавать четыре отдельных источника истины.

Критерий готовности: локально доступны точные ответы «кто вызывает», «где подключён сигнал», «какие сцены используют ресурс» и «что затронет переименование».

## Этап 8. Пакетные транзакции

Добавить действие верхнего уровня:

```json
{
  "action": "transaction",
  "operations": [
    {"action":"create_file","path":"res://player/health.gd","content":"..."},
    {"action":"add_node","scene":"res://player/player.tscn","parent":"Player","type":"Node","name":"Health"},
    {"action":"attach_script","scene":"res://player/player.tscn","node":"Player/Health","path":"res://player/health.gd"},
    {"action":"connect_signal","scene":"res://player/player.tscn","from":"Player/Health","signal":"died","to":"Player","method":"_on_died"}
  ],
  "checks": [
    {"type":"parse_script","path":"res://player/health.gd"},
    {"type":"load_scene","path":"res://player/player.tscn"}
  ]
}
```

Пайплайн транзакции:

1. Проверить схему и зависимости между операциями.
2. Создать staging-копию или in-memory overlay затронутых файлов.
3. Применить операции к кандидату.
4. Запустить локальные линтеры.
5. Запустить проверку Godot.
6. Показать пользователю единый preview.
7. После подтверждения атомарно применить пакет настолько, насколько это возможно на файловой системе.
8. Записать всю операцию одной цепочкой в существующий журнал.
9. При сбое восстановить все затронутые файлы.

План остаётся пользовательским представлением большой задачи, но его детерминированные шаги могут исполняться пакетами без отдельного обращения к модели на каждый шаг.

Критерий готовности: взаимозависимые скрипт и сцена проверяются совместно до попадания любого из них в рабочий проект.

## Этап 9. Высокоуровневые команды

Добавлять команды только поверх уже проверенного структурного исполнителя и семантического индекса:

- `rename_symbol`;
- `rename_node_references`;
- `create_component`;
- `extract_resource`;
- `duplicate_scene_branch`;
- `create_animation`;
- `add_animation_track`;
- `create_collision_shape`;
- `replace_resource`;
- `move_resource_with_dependencies`;
- `update_signal_connections`.

Каждая команда должна раскрываться в обычную транзакцию, чтобы использовать единые preview, проверки и откат. Не следует создавать отдельный механизм применения для каждой команды.

## Этап 10. Ресурсы и импорт

Добавить безопасную работу через `ResourceLoader`, `ResourceSaver` и `EditorResourcePreview`:

- создание и изменение `.tres`;
- `Animation` и треки;
- `SpriteFrames`;
- `Theme`;
- `TileSet` и его источники;
- замена ссылок на ресурс;
- чтение состояния импорта;
- ожидание окончания импорта после добавления ассета;
- создание превью для подтверждения пользователем.

Сначала реализовать универсальные операции загрузки, проверки типа и сохранения ресурса. Специализированные редакторы `TileSet`, анимаций и тем добавлять отдельно, потому что у них разные инварианты и высокая цена ошибки.

## Этап 11. Интеграция с отладчиком

Исследовать и подключить `EditorDebuggerPlugin`, `EditorDebuggerSession`, `EngineDebugger` и небольшой debug-only runtime bridge.

Доступный агенту контекст:

- дерево запущенной сцены;
- значения запрошенных свойств;
- stack trace и runtime errors;
- активная сцена;
- orphan nodes;
- основные метрики кадров;
- пользовательские диагностические события.

Изменяющие runtime-команды разрешать только в debug-запуске и после явного подтверждения. По умолчанию интеграция должна быть read-only.

Критерий готовности: после падения игры агент получает агрегированный stack trace и связанные исходники одним контекстным пакетом.

## Этап 12. Локальные игровые проверки

Реализовать небольшой детерминированный исполнитель сценариев, а не общий визуальный автотестовый фреймворк:

```json
{
  "action": "run_check",
  "scene": "res://levels/level_01.tscn",
  "steps": [
    {"wait_frames": 3},
    {"press": "move_right", "duration": 1.0},
    {"assert_property": {"node": "Player", "property": "position:x", "gt": 100}},
    {"assert_no_errors": true}
  ]
}
```

Минимальные возможности:

- запуск конкретной сцены;
- ожидание кадров и времени;
- ввод через InputMap;
- чтение узлов и свойств через debug bridge;
- утверждения о существовании, типе и значении;
- сбор ошибок;
- необязательный снимок экрана для пользователя.

Сценарий проверки может быть частью транзакции, но его неуспех не должен автоматически вызывать бесконечные исправления моделью.

## Порядок реализации

Рекомендуемая последовательность с учётом зависимостей и экономии запросов:

1. Контекст живого редактора с измеряемым бюджетом.
2. Составной `gather_context`.
3. Базовый семантический индекс объявлений, ссылок и зависимостей.
4. Безопасное переименование функций, сигналов и классов.
5. Структурные команды сцен.
6. Структурные настройки проекта для InputMap и autoload.
7. Проверка настоящим Godot поверх существующих линтеров.
8. Пакетные транзакции и атомарный откат по кнопке.
9. Переименование узлов, путей, групп и ресурсов.
10. Высокоуровневые команды и работа с ресурсами.
11. Debugger bridge.
12. Локальные игровые проверки.

Первые два этапа уменьшают число разведочных запросов. Этапы 3–7 уменьшают ошибки слабых моделей. Транзакции объединяют эти возможности в один безопасный цикл исполнения. Runtime-интеграция выполняется после стабилизации редактирования, чтобы не смешивать две сложные границы одновременно.

## Общие критерии безопасности

- Ни одно изменение проекта не применяется без preview и подтверждения, кроме уже разрешённых пользователем шагов подтверждённого плана или транзакции.
- Любая операция сообщает точный список затронутых файлов и ресурсов.
- Все изменения агента имеют адрес записи в существующем журнале.
- Откат агента не использует и не изменяет пользовательский стек Undo/Redo.
- Проверка выполняется до записи в рабочие файлы, когда это технически возможно.
- Неоднозначный рефакторинг не выполняется автоматически.
- Ошибка одной операции транзакции не оставляет применёнными остальные операции.
- Структурный исполнитель не переходит молча к небезопасной текстовой правке.
- Новые возможности получают feature flag до завершения живой проверки в Godot.

## Метрики результата

Для оценки пользы собирать локально без содержимого проекта:

- среднее число запросов модели на пользовательскую задачу;
- долю задач, выполненных одним запросом;
- размер постоянного и динамического промпта;
- число вызовов `read_file`, `list_scene`, Библиотекаря и `gather_context`;
- число отклонённых линтерами кандидатов;
- число ошибок, найденных только настоящим Godot;
- число успешных и неоднозначных рефакторингов;
- число автоматических откатов транзакций;
- долю структурных операций по сравнению с текстовой правкой сцен и ресурсов.

Главный показатель успеха: агент выполняет больше задач за один запрос, при этом не увеличивает количество повреждённых сцен, не смешивает пользовательский откат с откатом агента и не раздувает стартовый промпт.
