# План улучшения безопасного переименования (rename_symbol)

Документ для передачи **по одному этапу в отдельный чат**. Каждый этап
заканчивается рабочим состоянием репозитория и зелёными тестами — следующий
этап начинается только после этого.

## Как пользоваться этим документом

1. Отдать другому чату **один** этап (раздел «Этап N») целиком, вместе с
   разделами «Общие правила» и «Контекст проекта».
2. Дождаться отчёта: что изменено, какие тесты, какие решения приняты.
3. Передать следующий этап.
4. После последнего этапа — финальный аудит.

Этапы зависят по порядку: Этап 2 опирается на формат отчётов из Этапа 1,
Этап 3 — на доказательство из Этапа 2.

## Общие правила для любого этапа

**Процесс обязателен:**

1. **Сначала синтетика.** Тесты, описывающие требуемое поведение, ДО кода.
2. **Увидеть красный.** Прогнать и убедиться, что падение по делу
   (падение из-за отсутствующей функции — законный первый красный).
3. **Код.**
4. **Та же синетика** должна стать зелёной.
5. **Аудит** — отдельный проход с обоснованием.

# Этап 1. Гранулярность отказа

**Цель:** одна недоказанная ссылка больше не обнуляет всё переименование.

## Что происходит сейчас

В `prepare_rename` (1479–1559) каждая ссылка проходит цепочку проверок:

```python
if _reference_is_safe(...):                          # 1512
    edits_by_path.setdefault(path, []).append(...)    # принять
elif (другая сущность — чужой вложенный класс):      # 1522
    continue                                          # молча пропустить
elif _reference_in_other_scope(...):                 # 1529
    continue
elif (локальная тень):                               # 1534
    continue
else:
    ambiguities.append("%s:%s:%s" % (path, line, column))   # 1541

if ambiguities and mode == "strict":                 # 1557
    raise UnsafeRenameError(...)                     # 1558 — отменяет ВСЁ
```

Три `continue` — доказанно другая сущность, их пропускать молча верно.
Иначе попадает `ambiguities` — и это отменяет операцию целиком.

Измерено на живом проекте: база и прямой наследник содержат доказуемо
безопасные ссылки, но две сомнительные ссылки в посторонних файлах обнуляют
все правки.

## Что требуется

Разделить две категории:

1. **Ссылка доказуемо не наша** — не трогать, не показывать (уже есть).
2. **Ссылка наша, но не доказана** — не трогать, **показать, не отменяя**.

Пункт 2 сейчас отменяет всё. Требуется, чтобы недоказанные ссылки не
блокировали запись, но каждая была видна в отчёте ДО записи.

**Поведение по умолчанию молча менять нельзя.** `strict` обязан сохранить
текущее поведение — регрессия недопустима. Выбрать одно из двух (обосновать
в отчёте):

- **(А)** новый режим `best-effort` рядом с `strict` и `probable`;
- **(Б)** флаг `allow_unverified` в action, `probable` не трогать.

Критерий: у `probable` уже семантика «пользователь принял риск». Вариант (А)
честнее отделяет риск из-за динамики от риска из-за неполного анализа.

## Обязательные тесты

1. База с переменной, прямой наследник, **одна** недоказанная ссылка в
   постороннем файле: в новом режиме переименование **проходит**,
   доказанные ссылки переименованы, недоказанная — нет.
2. Тот же проект в `strict`: отказ, ничего не изменено. Регрессия.
3. Недоказанная ссылка **присутствует в отчёте** с путём и координатами.
4. Отчёт содержит счётчики: сколько переименовано, сколько не доказано.
5. Нет недоказанных ссылок → отчёт без пустых секций.
6. Регрессия локальной тени: одноимённая локальная переменная по-прежнему
   пропускается молча и **не** попадает в недоказанные.

## Границы этапа

- Не трогать `_reference_is_safe` — это Этап 2.
- Динамические ссылки (`ClassDB.instantiate("X")`) остаются отказом в `strict`.
- Не менять `apply_prepared_rename`.
# Этап 2. Транзитивное наследование как доказательство

**Цель:** `self.x()` во внуке распознаётся как ссылка на член базового класса.

## Что происходит сейчас

`_find_subclasses` (442) обходит иерархию **транзитивно** (BFS с очередью) и
возвращает все скрипты-потомки. Результат передаётся в `_reference_is_safe`
как `subclasses` и `all_target_classes`.

Там же:

```python
same_script = path == target_path
is_subclass = bool(subclasses and path in subclasses)
hierarchy = same_script or is_subclass          # 806

if prev_value == ".":                            # 808
    if hierarchy and receiver == "self" and in_script:
        return True
```

Формально `hierarchy` для внука истинен. Но измерено: проект
`SlimeBoss extends Slime extends BaseEnemy` с чистым `self.health`
в `SlimeBoss` **получает отказ**.

Значит отказ приходит не отсюда. Требуется **сначала установить точную
причину**: в `_owner_shadows_name`, `_owner_belongs_to_script`,
`_reference_in_other_scope` или ещё где-то. Не начинать правку, не найдя
причину — иначе получится «лечим не тот симптом».

## Что требуется

1. **Диагностика.** Воспроизвести на живом проекте и определить, какая
   именно проверка возвращает `False` для `self.health` в внуке.
2. **Исправление** найденной причины, а не ослабление проверок.
3. Если окажется, что `self.x()` во внуке **недоказуем** в общем случае —
   не «лечить» это допущением, а зафиксировать границу в отчёте и тесте
   (как `dynamic_references`).

## Обязательные тесты

1. `A ← B ← C` (два уровня): `self.member` в `C` переименовывается.
2. Тот же случай с `method()` в `C`.
3. `self.member` в `C`, где `C` объявляет **собственное** поле с тем же
   именем — не переименовывается (доказанно другая сущность).
4. `self.member` в скрипте **вне** иерархии — не переименовывается.
5. Регрессия всех существующих `test_rename_*`.
6. Уровень `class_name` через цепочку: `C extends B`, где `B` переименовывал
   `class_name` — поведение не хуже текущего.

## Границы этапа

- Только `self` и явный receiver с типом. Никаких догадок о типе выражения.
- Если причина окажется в `_owner_belongs_to_script` — там обоснование
  про вложенные классы тонкое, ослабление сломает `test_rename_nested_members`.
- Не трогать динамические ссылки и Этап 1.

# Этап 3. Доступ к режиму `probable`

**Цель:** режим, который уже реализован, должен быть достижим из интерфейса.

## Что происходит сейчас

`MODES = ("strict", "probable")` объявлено в строке 107. При `probable`
недоказанные ссылки превращаются в `unverified_references` (1564) и запись
продолжается; динамические ссылки показываются, но не блокируют (1567).

Поиск по всему проекту дал **только** объявление `MODES` и текст подсказки
внутри самой ошибки (строка 1578). Ни панель, ни агент, ни MCP это поле не
выставляют.

Итог: функция есть, путь к ней закрыт. Пользователь не может выбрать
`probable`, кроме как вручную дописав его в JSON-действие.

## Что требуется

1. Найти, где формируется action `rename_symbol` для панели и для агента.
2. Дать пользователю способ выбрать режим — так, чтобы выбор был **виден и
   осознан**, а не молчаливым переключением.
3. Текст подтверждения обязан объяснять риск: «список мест не будет
   переименован, проверьте вручную».

## Обязательные тесты

1. Панель/агент передаёт выбранный режим в action без потери.
2. `strict` остаётся режимом по умолчанию.
3. Путь до режима доступен и читаем (тест на наличие элемента или функции,

4. Регрессия: `test_rename_refusal_levels.py` целиком.

## Границы этапа

- Не менять семантику самого `probable` — только доступность.
- Не расширять Этапом 1 на `strict`.
- Если выяснится, что режим намеренно скрыт как незавершённый, — не
  открывать, а зафиксировать это в отчёте как решение с обоснованием.

# Этап 4. Полнота семантического индекса

**Цель:** один сломанный файл в углу проекта не блокирует переименование.

## Что происходит сейчас

```python
if not snapshot.get("complete"):                     # 1307
    raise RenameError("Семантический индекс неполон; ...")
partial = [path for entry in ... if parse_status != "ok"]   # 1309
if partial:
    raise RenameError("Не удалось полностью разобрать GDScript: %s" % ...)
```

Отказ глобальный: любой файл, который парсер не понял (зависимость от
GDExtension, нестандартный синтаксис, битая кодировка), блокирует
переименование **везде**.

## Что требуется

Оценить, безопасно ли частичное применение: если файл вне иерархии целевого
символа и не содержит его имени, его неразобранность **не влияет** на
корректность переименования.

Осторожность обязательна. Текущий отказ может быть осознанным: «не знаем всё
проекта — не обещаем ничего». Тогда правильный ответ — сузить отказ
(«неразобран файл X, он вне иерархии цели»), а не отменять его.

## Обязательные тесты

1. Неразобранный файл **вне** иерархии и без упоминания имени → переименование
   проходит, в отчёте есть предупреждение о нём.
2. Неразобранный файл **внутри** иерархии → отказ, ничего не изменено.
3. Неразобранный файл, содержащий искомое имя → отказ.
4. Регрессия `test_rename_refusal_kinds.py`.

## Границы этапа

- Не ослаблять отказ, пока не доказано, что неразобранный файл не влияет
  на результат именно для этого символа.
- Если сузить отказ нельзя безопасно — оставить как есть и зафиксировать
  в отчёте: тогда это осознанное решение, а не упущение.

# Финальный аудит

Проводится после всех этапов. Ожидаемые темы:

1. Ни одна существующая проверка не ослаблена ради прохождения тестов.
2. Каждый новый отказ/предупреждение честен: недоказанное названо
   недоказанным, а не «переименовано».
3. Нет молчаливых правок: любое место, которое не тронули, видно в отчёте.
4. `strict` по умолчанию ведёт себя как раньше.
5. Циклы и вложенность не сломаны.
6. Новые тесты падали бы на старом коде (проверяется откатом коммита).
