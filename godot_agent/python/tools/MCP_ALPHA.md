# MCP ALPHA v0 — мост между внешней нейросетью и плагином Godot_agent

Этот файл — системная инструкция для нейросети, работающей с проектом Godot
снаружи редактора (Cline, Cursor, терминал). Вставь его в промпт целиком.

Ты получаешь доступ к командной утилите `agent_bridge.py`, которая отвечает
из ТЕХ ЖЕ источников данных, что и встроенный агент плагина (кэш Godot API,
Библиотекарь, поиск по проекту, движок переименований). Её ответы — актуальное
состояние проекта и движка. Твоя обучающая выборка про Godot API может
устареть или не знать этого проекта — при расхождении ВЕРИТЬ МОСТУ.

## Запуск

```
python "<аддон>/python/tools/agent_bridge.py" [--root <путь к проекту>] [--access project|addon|agent-dev] [--godot <путь к Godot>] [--validation off|auto|required] <команда> [аргументы]
```

`--root` можно не указывать, если рабочая папка — внутри проекта (мост сам
поднимается вверх до `project.godot`). Сервер плагина для большинства команд
НЕ нужен: мост читает файлы и кэши напрямую.

## Режимы доступа

| Режим | Обычные файлы | Внешние `addons/` | Текущий Godot Agent |
|---|---:|---:|---:|
| `--access project` | да | нет | нет |
| `--access addon` (по умолчанию) | да | да | нет |
| `--access agent-dev` | да | да | да |

`agent-dev` — специальный developer mode для саморазвития Godot Agent. Он
разрешает запись только в корень, который мост вывел из собственного
исполняемого исходника/модуля; модель не может передать другой `addon_dir`.
Если корень текущей установки не удалось определить, режим `agent-dev`
не открывает никакие файлы. Режим `addon` — это НЕ доступ к текущему агенту:
он открывает только внешние аддоны.

`--godot` передаёт путь к настоящему Godot для изолированной проверки
кандидата. `--validation off` отключает headless-проверку (для быстрых
локальных тестов), `auto` проверяет Godot при наличии, `required` запрещает
apply без настоящей проверки.

Режим влияет и на `check`, а не только на `write apply`. При
`--validation required` отсутствие настоящего Godot означает, что проверка
НЕ выполнена: мост не скажет «clean», а вернёт код 3 и напечатает
`headless: unavailable` вместе с причиной. Код 3 здесь — честный отказ
«инструмент не смог ответить», а не утверждение о чистоте файла. При
`auto` проверка не обязательна, но `check` всё равно печатает фактический
статус headless-проверки, чтобы отсутствие Godot не выглядело как
успешная проверка.

## Команды

| Команда | Что даёт |
|---|---|
| `status` | жив ли сервер плагина, принимает ли наш токен, состояние кэша API |
| `engine` | версия Godot проекта и источник кэша API |
| `api <ClassName>` | методы/свойства/сигналы класса со ВСЕЙ цепочкой наследования; при свежем кэше — ПОЛНЫЕ сигнатуры (`move_and_slide() -> bool`, `set_velocity(v: Vector2) -> void`) |
| `ask <запрос>` | компактная справка о проекте (Библиотекарь: карта кода, фрагменты, вызовы) |
| `search [--max N] <текст>` | поиск подстроки по текущему режиму доступа; `N` — положительное целое число |
| `read [--max-chars N] <res://path>` | прочитать один разрешённый файл; в `agent-dev` можно читать текущий Agent |
| `context --request FILE` | тот же bounded local evidence, что собирает встроенный агент: символы, зависимости, diagnostics, project settings, справка Godot API |
| `check <res://path...>` | детерминированная проверка: `gd_lint` + `gd_api_check` для `.gd`, `tscn_lint` для `.tscn`, синтаксис для `.py`/`.json`/`.cfg`, плюс настоящий headless Godot; печатает строку `headless: <статус>` |
| `check_action --request FILE` | локальный Judge одного действия модели (`{"text": ...}`) без записи и без вызова нейросети |
| `paths preview <old> <new>` | предпросмотр переименования/перемещения: счётчики ссылок, затронутые файлы |
| `write preview --request FILE` | подготовить `create_file`/`patch_file`/`move_file`/`repair_scene`/`rename_symbol` или `transaction`; исходники не меняются |
| `write apply --request FILE --plan-id ID` | применить ранее подготовленный и одноразовый план |
| `write rollback --entry-id ID [--force]` | адресный откат записи журнала; `--force` только для ручного конфликта |

`move_file` через `write` использует тот же безопасный file-refactor, что и встроенный агент: обновляет точные `res://`-ссылки в `.gd`, `.tscn`, `.tres`, `project.godot`, внутренние относительные `preload/load/extends`, companion `.import`, сохраняет `.uid` и создаёт адресный rollback. `move_file` нельзя смешивать с create/patch внутри `transaction` — отправляйте его отдельным запросом.

### Квитанции планов и уборка мусора

Каждый `write preview` оставляет одноразовую квитанцию `<plan_id>.json` в
`<user://>/agent_history/bridge_plans/`. `write apply` атомарно переименовывает
её в `<plan_id>.json.applying-<pid>`, а после успеха удаляет.

Мост САМ убирает мусор при каждом `write preview` и `write apply`: удаляет
квитанции `.json` старше 15 минут, а также `.applying-<pid>` — **только если
процесс с этим pid доказанно мёртв**. Живой apply не трогается никогда, даже
если его квитанция старая; если состояние процесса определить не удалось
(например, нет прав на проверку) — файл тоже остаётся. Запасного «срока
старости» для `.applying-<pid>` нет намеренно: он рано или поздно удалил бы
чужую живую работу, а пользы не приносит.

Файл `.applying-<pid>` — это маркер «apply шёл», а не источник правды:
одноразовость плана держится на том, что `<plan>.json` уже переименован. Так
что оставшийся маркер безвреден и исчезнет, как только процесс завершится.

Уборка best-effort: нет прав или каталога — она молча ничего не делает и
работу не ломает.

Если мост упал во время apply, останется файл `<plan_id>.json.applying-<pid>`;
он исчезнет сам при следующем preview/apply. Сам `plan_id` после этого
непригоден — он одноразовый, просто сделай новый `write preview`. Если файл
`.applying-<pid>` не исчезает долго, значит указанный процесс всё ещё жив (или
у моста нет прав на удаление) — это информация для оператора, а не повод
удалять файл вручную во время активного apply.

## Автономные безопасные инструменты

Эти возможности работают без сервера, панели агента и нейросети.

`context --request FILE` собирает локальный контекст тем же кодом, что и встроенный агент (`gather_context.gather`), но без EditorContext. Запрос задаёт `query`, `symbols`, `godot_api`, `max_chars` и флаги секций. Это предпочтительнее десятка `read`/`search`: он сразу возвращает символ, его зависимости, diagnostics и релевантные настройки проекта в ограниченном бюджете символов.

`check <res://path...>` — read-only проверка. Для `.gd` работают `gd_lint` и `gd_api_check`, для `.tscn` — `tscn_lint`, для `.py`/`.json`/`.cfg` — локальный синтаксис. Для Godot-типов дополнительно запускается изолированная headless-проверка, если доступен `--godot`; строка `auto_fixable: true` означает, что `tscn_lint` нашёл однозначные механические исправления.

Для каждого пути печатается строка `headless: <статус>` — `passed` / `failed` /
`inconclusive` / `unavailable` / `skipped`, либо `not-applicable` для типов без
headless-проверки (`.py`, `.json`, `.cfg`). Никогда не делай вывод о чистоте
`.gd`/`.tscn` по строке `headless: unavailable` или `headless: skipped`: это
значит, что настоящий Godot файл НЕ проверил. Если headless-проверка
заблокирована (нет executable, таймаут, падение), мост добавляет это в
`problem:` и возвращает код 3 — это отказ «инструмент не смог ответить»,
а не подтверждение чистоты.

Для каждого пути печатается также строка `truncated: true|false` — проверялся
ли файл целиком. Линтеры `check` получают файл ПОЛНОСТЬЮ (лимит 2 097 152
символа — это страховка от файлов размером с память, а не рабочий предел).
Если `truncated: true`, файл проверен частично: мост добавляет `problem:` с
точными числами («проверено 2097152 из 3000014») и возвращает код 2.
Частичная проверка никогда не выглядит как `clean`: дефект в хвосте большого
файла — обычное дело, поэтому при `truncated: true` не делай выводов о
чистоте и разбей файл на части (`read --max-chars`) либо найди его
источник.

Для каждого пути печатается строка `checked: true|false` — **выполнилась ли
хотя бы одна проверка фактически** (а не просто «расширение чем-то
проверяемо»). Разница существенна:

- `.gd`, `.tscn`, `.py`, `.json`, `.cfg` — есть локальный линтер, поэтому
  `checked: true` даже без настоящего Godot;
- `.tres`, `.gdshader`, `.shader` — их умеет проверять **только** настоящий
  Godot. Пока он не отработал (`headless: unavailable` / `skipped`), не
  выполнено НИ ОДНОЙ проверки, и мост честно ставит `checked: false` с
  пояснением. С работающим Godot — `checked: true`.

Непроверяемый файл получает строку `check_skipped: <причина>`. В конце
выводится итог `checked: k/n`; при `k < n` код возврата 2, потому что слово
«clean» относится только к тем `k` файлам, которые действительно проверились.
При `checked: 0/n` ты не получил проверки вообще — не сообщай пользователю,
что файл в порядке. `checked: false` — это НЕ ошибка, исправлять файл не
нужно.

`check_action --request FILE` локально судит одно действие модели: принимает `{"text": "..."}` с обычным текстом ответа (включая блок `agent_action`) и возвращает `score`, `acceptable`, `blocking`, `warnings`, `evidence`. Ничего не пишет и не вызывает модель. Используй его перед `write preview` для своего же действия.

### `repair_scene` — частичное автоисправление сцен

```json
{"action": "repair_scene", "path": "res://scenes/level.tscn"}
```

Это единственный разрешённый способ изменить `.tscn` через мост. Прямой `create_file`/`patch_file` в `.tscn` по-прежнему отклоняется. `repair_scene` вызывает `tscn_lint.lint_and_fix_tscn` и применяет только те исправления, которые линтер считает однозначными: перестановку секций, `load_steps`, удаление закрывающих `[/node]`, порядок узлов по родителю, битые ссылки, конструкторы в `sub_resource` и подобные механические дефекты.

preview показывает `plan_id`, diff и строки `remaining_problem:` для всего, что линтер исправить не смог. Если остались неоднозначные проблемы, а текст изменить нельзя, preview честно откажется с кодом 2. `apply` повторно проверяет хэш, политику и headless-валидацию, пишет через журнал и поддерживает `write rollback`. Семантические правки сцены (новые узлы, переустановка скриптов) в этот инструмент НЕ входят — для них нужен редактор.

Для `search` после `--max` обязательно указывается положительное целое число,
а после удаления самой опции должен оставаться непустой поисковый запрос.
Отсутствующее, нечисловое или неположительное значение `--max`, пустой запрос
и ПОВТОР `--max` возвращают код 4 (`usage`).

## Коды возврата

| Код | Значение | Когда выдаётся | Твоё действие |
|---:|---|---|---|
| 0 | ok | данные в stdout | работай с ними |
| 2 | not-found | запрошенного НЕ СУЩЕСТВУЕТ или отказ политики по существу | факт: искомого нет; переформулируй |
| 3 | error | инструмент НЕ СМОГ ответить: нет кэша, недоступен обязательный Godot, потеряна квитанция плана или запись журнала | сообщи пользователю; НЕ ищи причину в несуществующем объекте |
| 4 | usage | неверные аргументы, битый/нечитаемый JSON запроса, дубликат опции | исправь ВЫЗОВ и повтори |

Важное различие: **2 — это про мир** («такого класса/совпадения/файла нет»),
**3 — про инструмент** («мост не смог: нет квитанции плана, журнал недоступен,
обязательный Godot не запустился»). Квитанцию плана и журнал создаёт сам мост,
поэтому их отсутствие — это 3, а не 2. Никогда не переводи отказ моста в
«запрошенного не существует»: при 3 искомый объект может существовать, ответ
просто не был получен.

## Предупреждения о режиме доступа

Если в stdout встретилась строка `warning: access mode 'addon' degraded to
'project'`, мост НЕ нашёл доверенный корень Godot Agent и внешние аддоны в
этом режиме недоступны. Результат `search`/`read` верен только для обычных
файлов проекта: отсутствие совпадений НЕ означает, что их нет в аддонах.
Перечитай `MCP_ALPHA.md` про режимы доступа и не делай выводов об аддонах.

## ЖЁСТКИЕ ПРАВИЛА

1. **Никогда не пиши напрямую и не вызывай `write apply` без preview.**
   Для каждого изменения сначала подготовь JSON-файл, запусти
   `write preview`, проверь `plan_id` и diff, и только затем повтори тот же
   запрос с `write apply --plan-id`. План одноразовый и живёт 15 минут.
   В режиме `addon` не пытайся писать в текущий Godot Agent; для этого
   явно запускай `--access agent-dev`.

2. **Проверяй код возврата после КАЖДОГО вызова.** Читать stdout имеет
   смысл только при коде 0 или 2. Статусная строка в stderr:
   `bridge: ok|not-found|error|usage: <пояснение>`.

3. **Код 3 (error) — инструмент НЕ СМОГ ответить.** Сюда относятся, в
   частности: потерянная квитанция плана (`plan receipt not found`), нет
   записи журнала для `write rollback`, недоступный обязательный Godot,
   недоступный доверенный корень в `agent-dev`. Ты ОБЯЗАНА явно сообщить
   пользователю: «функция X не сработала: <причина из stderr>». Запрещено
   молча подставлять свои догадки. Если продолжаешь работу на собственных
   знаниях — скажи это прямо. НИКОГДА не переводи отказ 3 в «объекта не
   существует»: искомый объект может быть на месте, ответ просто не получен.

4. **Код 2 (not-found) — это ОТВЕТ, а не сбой.** Запрошенного не
   существует: класса нет в этой версии движка, совпадений нет, файла-
   источника нет, назначение занято, либо отказ политики доступа по существу
   (запись в чужой аддон, в `project.godot`, в защищённый каталог агента).
   НЕ сообщай об этом как об «ошибке инструмента» и НЕ повторяй
   идентичный запрос. Используй как факт: «такого в проекте/движке нет —
   меняю план».

5. **Подводный камень «требуемого не существует».** Если ты получила
   not-found дважды подряд по соседним формулировкам — остановись: почти
   наверняка ты ищешь то, чего нет в принципе (устаревший класс Godot 3.x,
   выдуманный метод, чужое API). Не перебирай варианты вслепую — скажи
   пользователю, что искомое не находится, и предложи альтернативу из
   реально найденного (например, ближайший базовый класс из `api`).

6. **Код 4 (usage) — ты неправильно вызвала команду.** Сюда относятся и
   ошибки самого запроса: отсутствующий `--request`, нечитаемый или битый
   JSON, дубликат ключа в JSON, повтор `--max`. Это ошибка ТВОЕГО вызова —
   исправь файл запроса или аргументы и повтори; искомый объект тут ни при
   чём. Если нужной возможности у моста нет — скажи «мост этого не умеет»,
   не имитируй результат другими командами и не выдумывай данные.

7. **Сервер недоступен (status → DOWN).** Предупреди пользователя одной
   фразой и продолжай: `engine/api/ask/search/read/paths/write` работают
   офлайн. Недоступны только операции, требующие живого редактора.

## Что мост НЕ умеет (живой редактор)

Эти возможности встроенного агента не переносятся в stdio-MCP обёрткой, потому что их apply выполняется через `EditorInterface` в панели Godot:

- `create_scene` и `edit_scene` — создание сцен, добавление/перенос/удаление узлов, подключение сигналов и скриптов;
- структурный node refactor (reparent, переустановка скрипта, переименование узла);
- `edit_resource` — операции через импортёр и инспектор ресурсов;
- `edit_project_settings` — применение через `ProjectSettings`;
- `inspect_runtime` / `run_check` — требуют запущенной игры и runtime bridge;
- несохранённые вкладки редактора и `post_move_sync` после move;
- чаты, голос и любые AI-провайдеры — требуют внешних API и моделей.

Их Python-часть (`scene_actions.prepare`, `resource_actions.prepare`, `project_settings_actions.prepare`) уже умеет валидировать и нормализовать операцию, поэтому она используется в `check_action` как read-only проверка. Для полноценного автономного apply структурных операций нужен отдельный headless-исполнитель, запускающий настоящий Godot, а не текстовая запись в `.tscn`. Пока его нет, мост честно отказывает, а не делает вид, что записал сцену.

Если ты получила отказ на такой операции, скажи пользователю ровно это: «структурное изменение сцены требует открытого редактора Godot; мост умеет только безопасное механическое `repair_scene`». Не выдумывай результат.

## Типовая сессия

```
# 0. Кто мы и что живо
python .../agent_bridge.py status

# 1. Актуальная версия движка (а не «по памяти»)
python .../agent_bridge.py engine

# 2. Перед использованием любого класса Godot — проверка сигнатур
python .../agent_bridge.py api CharacterBody2D

# 3. Ориентирование в проекте (обычный режим)
python .../agent_bridge.py --access addon ask player movement collision
python .../agent_bridge.py --access addon read res://src/player.gd

# 4. Перед изменением кода агента: явный developer mode + preview
python .../agent_bridge.py --access agent-dev read res://addons/Godot_agent/godot_agent/agent_panel.gd
# подготовь request.json, затем:
python .../agent_bridge.py --access agent-dev write preview --request request.json
# проверь plan_id и diff, затем повтори:
python .../agent_bridge.py --access agent-dev write apply --request request.json --plan-id <ID>

# 5. Перед предложением переименования — предпросмотр последствий
python .../agent_bridge.py paths preview res://src/player.gd res://src/actors/player.gd
```

## Ограничения v0 (честно)

* Это НЕ настоящий MCP-stdio-сервер, а CLI + инструкция. Настоящий MCP —
  отдельный следующий шаг (нужен пакет `mcp` и конфиг клиента).
* `write preview` — единственная фаза, на которой исходники не меняются;
  `write apply` записывает только один ранее проверенный plan и создаёт
  journal entry. `write rollback` откатывает конкретную запись.
* `write` поддерживает текстовые `.gd`, `.py`, `.json`, `.cfg`, `.md`,
  `.gdshader`, `.shader`, `.csv`, `.txt`; `project.godot`, `.tscn` и
  сгенерированные frozen/utility paths нельзя менять этим каналом.
* `--access addon` (по умолчанию) работает с обычными файлами и внешними
  аддонами; `--access agent-dev` добавляет текущий Godot Agent и должен
  включаться пользователем явно. Это локальный developer mode, не замена
  политике панели и не безопасный sandbox для вредоносного процесса.
* `ask` может создать локальный кэш/индекс и журнал в `user://`/истории;
  это не означает применение изменений к исходникам.
* `paths preview` остаётся полностью read-only. Его apply намеренно
  оставлен панели агента, где есть синхронизация с открытым редактором.
* `write` и `paths preview` не должны выполняться параллельно с другими
  writers одного проекта: текущий history lock сериализует потоки внутри
  процесса, но не заменяет межпроцессный OS-lock.
* `ask` при холодном старте строит индекс проекта на лету — первый запрос
  может занять секунды. Это нормально, не отменяй по таймауту раньше ~60 c.
* Кэш API бывает двух видов: выгруженный этим проектом (`project export`,
  точно соответствует его движку) и встроенный в аддон (`builtin addon
  cache`, версия указана в выводе `engine`). Всегда смотри, какой из них
  ответил, и называй версию пользователю.
* Полные сигнатуры методов (имена/типы/умолчания аргументов и тип
  возврата) появляются только в кэше нового формата. Если `api` печатает
  компактную строку арности `name(min..max)` — кэш старый: попроси
  пользователя нажать «Обновить справочник API Godot» в панели агента,
  после чего переспроси `api`. На старом кэше сверяйся хотя бы по арности.
* `paths preview` учитывает `--access`; его apply всё равно оставлен панели
  агента, где есть синхронизация с открытым редактором.
* Токен сервера мост читает из `user://godot_agent_token.txt` сам;
  переопределение — `--token` / переменная `GODOT_AGENT_TOKEN`,
  `--udd` — путь к user:// вручную.
