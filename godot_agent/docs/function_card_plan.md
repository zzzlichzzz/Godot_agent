# План: глубокая карточка функции (`function_card`)

Статус: **обсуждение с владельцем, 15.10.2026** — план пишется до начала работ.
Это продолжение закрытого **L7** («карточка символа»,
`docs/librarian_search_plan.md` §5): там карточка отдаёт объявление, локальные
переменные и все ссылки по проекту. Здесь договариваемся, чего в ней не хватало.

## 1. Проблема (сценарий владельца)

Модель просит `func take_damage` из `res://scripts/base/base_enemy.gd`. Сейчас
ей приходится собирать контекст несколькими запросами, а часть связей она
вообще додумывает. Нужен ОДИН ответ, который даёт:

1. **Тело функции целиком** — дословно, не режется никогда.
2. **Все символы, которые тело трогает** — по одному на строку, с файлом и
   номером строки объявления, сгруппированные по источнику.
3. **Связи самой функции по проекту** — включая наследование, которое grep
   не видит: наследник не пишет `take_damage` текстом, но функция в нём живёт.

Пример-эталон от владельца (полигон, `base_enemy.gd`): тело `take_damage`;
среди символов — члены `is_dead`, `base_block_chance`…; autoload
`GameManager.current_hero.heal(...)`; функции `_on_blocked`, `_die`…;
наследники `bat_enemy.gd`, `bomber_enemy.gd`, `demon_enemy.gd`, `rat.gd`,
`skeleton.gd` — ни один не упоминает имя текстом.

## 2. Решения, к которым пришли

### 2.1. Формат секций

| Секция | Что отдаём | Почему так |
|---|---|---|
| Тело | дословно, всегда полное | главный контент; урезание ломает смысл |
| Символы тела | **все**, одной строкой каждый: `имя: тип = значение — файл:строка` | частичный список без пометки опаснее отсутствия; однострочник дёшев (~15 токенов) |
| Функции тела | **только имя + диапазон строк** (`_on_hit() :140–146`), без тела | модель точечно дожимает `functions --names`, не таща все тела; это граница, которая держит объём |
| Связи функции | три разных списка (§2.2) | см. семантику ниже |

Группы символов (обязательны, у каждой — `файл:строка` объявления):

- `members` — члены своего класса;
- `consts` — консты файла/класса;
- `autoload` — синглтоны проекта (`GameManager` → его скрипт) — именно их
  модель додумывает хуже всего;
- `external` — чужие `class_name`/консты (`LabConstants.BASE_HEALTH` и т.п.).

### 2.2. Три вида связей по функции — не смешивать

1. **«вызывается из»** — файлы, где `take_damage(` написано текстом. С grades
   `proven/probable/dynamic` из `usages`: динамические
   (`call("take_damage")`, `Callable`, `has_method`) статикой не ловятся —
   честная пометка.
2. **«наследники (получат функцию)»** — файлы, которые наследуют класс и НЕ
   упоминают имя. Смена сигнатуры их заденет, хотя grep их не найдёт.
3. **«переопределения»** — наследники, объявляющие ту же функцию (и обычно
   зовущие `super.take_damage()`). При правках это отдельная, важнейшая связь.

Связывать наследников **по иерархии классов, а не по имени по всему проекту**:
на полигоне у `take_damage` два разных объявления (`base_enemy.gd` и
`base_hero.gd`) — слияние по имени даст ложные связи.

Данные уже есть, пересборки индекса не нужно:
- `extends` пишется в карточку донора семантического парсера
  (`gd_semantic_parser.py`);
- поиск подклассов уже реализован в движке переименований
  (`symbol_refactor_part2.py`, `_find_subclasses`);
- ссылки со счётчиками и grades — из L7 (`librarian.py`, семантический индекс
  с mem-кэшем).

Новая работа — это join «иерархия × упоминания» + форматирование, не новый
парсер.

### 2.3. Лимиты и честные хвосты (нагрузка на контекст)

Прикидка владельца подтверждена: эталонная карточка ≈ **600–900 токенов** —
копейки. Опасен только один случай — встраивание **тел** внешних функций, и мы
его отсекли (имена + адреса вместо содержимого; глубина — ровно один хоп,
без транзитивного разрастания).

Лимиты на секции (значения уточним замером, стартовые):

| Параметр | Старт | Переполнение |
|---|---|---|
| `CARD_MAX_MEMBERS` | 24 | хвост `+N more` |
| `CARD_MAX_FUNCS` | 16 | хвост `+N more` |
| `CARD_MAX_CALL_FILES` | 12 | хвост + счётчик ссылок (как в L7: «43 ссылки в 20 файлах») |
| `CARD_MAX_SUBCLASSES` | 12 | хвост + общий счётчик |
| `CARD_MAX_OVERRIDES` | 8 | хвост |

Наследников может быть >100 (широкие базовые классы) — поэтому не «выводим
всех», а: прямые наследники первыми, дальше по глубине/имени, честный
`+N more (всего N)`. Счётчик важнее списка: модели чаще нужно знать «сколько
и что заденет», чем перечислить сотню файлов.

Общий потолок карточки — `CARD_BUDGET_LINES ≈ 200 строк` на ответ; тело в этот
бюджет **не входит** (не режется никогда).

### 2.4. Устаревание строк после правок (детерминированная проверка)

Проблема владельца: после правки функции номера строк ниже по файлу сдвигаются,
и модель либо меняет «не свои» строки, либо вынуждена каждый раз переспрашивать
«а как сейчас выглядит код».

Три правила, все детерминированные:

1. **Запись уже безопасна по содержимому, а не по строкам.** Двухфазная запись
   моста (`write preview` → `plan_id` → `write apply`) применяет правку точным
   совпадением текста: если файл с тех пор изменился, правка не «проедет» мимо —
   она отклоняется. Порчи чужих строк по сдвинутым номерам нет по построению.
2. **`write apply` начинает возвращать пост-состояние.** После применения —
   пере-парс правленного файла: новые диапазоны изменённых функций, число строк,
   применённый диф. Модель видит результат правки в том же ответе и не тратит
   отдельный запрос на «проверить, что получилось». Это и есть детерминация
   «хочу увидеть, что с кодом сейчас».
3. **Карточка несёт штамп версии файла** (sha1/mtime+size). Любой инструмент,
   отдающий номера строк, сверяет штамп; при устаревании номера пересчитываются
   по свежему индексу (дёшево — индекс в памяти, mem-кэш `_SEM_MEM_CACHE` уже
   есть) и ответ честно помечается «пересчитано, файл менялся после чтения».

Итого: проверка правки — это совпадение **анкора (нормализованного текста)**,
а не номера строки; номера в ответах всегда либо свежие, либо помеченные
пересчётом. Свежее состояние модель получает бесплатно, из пост-состояния
`write apply`.

Триггер глубокой карточки (предложение, требует подтверждения): голое имя —
базовая карточка L7 (как сейчас, дёшево для сцены); **`func:имя`** — глубокая.
Детерминировано и не раздувает ответы там, где тело не нужно. Промпт менять не
обязательно: префикс `func:` уже распознаётся.

## 5. Открытые вопросы — РЕШЕНО (15.10.2026, реализация S2–S6)

1. Триггер: **`func:`-префикс**, как предложено в §3 — реализовано в
   `librarian._symbol_card`: голое имя остаётся дешёвой карточкой L7, явный
   `func:имя` добавляет FUNC CARD после SYMBOL. В мосте/MCP — флаг
   `--card` / `card: true` у `functions` (там запрос всегда явный: файл+имя).
2. Лимиты §2.3 — стартовые значения вошли в реализацию как константы
   (`CARD_MAX_*` в `function_card.py`); замер на полигоне (`take_damage`)
   подтверждает достаточность для показа, хвосты честные. Валидация чисел
   отложена до обратной связи по реальным запросам.
3. Отдельный тул не нужен: FUNC CARD — **расширение** (внутри
   `librarian.answer`, внутри `functions` моста; нового «монолита» нет).
   Ядро живёт в `godot_tools/function_card.py` по правилу архитектуры.
4. Типизированные вызовы (`enemy.take_damage()`) попадают в слой probable
   как member-контекст — отдельного разрешения типов в v1 нет, честно
   помечено. См. раздел 6.
