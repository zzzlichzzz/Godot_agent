## Требование к стенду: перезапуск редактора после обновления панели

`agent_panel.gd` исполняется внутри запущенного Godot-редактора. После
обновления файла панели на диске уже открытый редактор продолжает работать
со **старой** версией скрипта. Любая живая UI-проверка панели допустима
только после **перезапуска редактора**; без него результат не относится
к новой версии панели.

## Что это значит для п.4 задачи

Прогон «rename константы обновляет использование в том же файле» подтверждён
живым HTTP-прогоном (раздел выше) плюс компенсационными проверками (по
отдельности не являются независимыми доказательствами):

- **API** (компенсация): `POST /chat` → `POST /chat/confirm_action`, rc=200, обе строки
  (19 объявление, 69 использование) переименованы, `reference_count=1`; скрипт
  `%TEMP%\n8n_hands_scratch\lab_rename_http_proof.py`, `LAB_HTTP_PROOF: PASS`;
- **MCP-мост** (компенсация): `agent_bridge.py write preview` → `write apply` → `write rollback`, rc=0,
  в диффе ровно два ханка (`@@ -16,7` и `@@ -66,7`), цикл rename→rollback→rename чист;
- **Браузер** (компенсация): `probe_rename_turret.py` (rc=0) на temp-копии проекта:
  вызовы `/chat` (rc=200) и `/chat/confirm_action` (rc=200, варианты (a) без exclude

Панель редактора использует те же `/chat` и `/chat/confirm_action`

## Ловушка: файл могут откатить «извне» (2026-10-24)

Через несколько минут после успешного переименования файл вернулся к исходному
содержимому (sha снова `9200e2c8…`). Сервер это заметил и сообщил агенту:

    [Система]: файлы проекта ИЗМЕНИЛИСЬ вне этого диалога (пользователь или другая программа)
    - изменён: res://src/refactor_lab/scripts/lab_root.gd — точечная правка …

При этом запись в журнале осталась «применённой»: журнал и диск разошлись
(кнопка отката предлагала откатить уже несуществующее изменение). Расхождение
снимается откатом записи через сервер — журнал и диск снова согласованы.

Что проверять, если «переименование пропало»:

- редактор мог перезаписать файл своим буфером (открытая вкладка скрипта):
  панель синхронизирует вкладку с диском, но при несохранённых правках буфер
  не трогает и предупреждает;
- любой другой процесс: автосохранение, внешний инструмент, второй экземпляр агента;
- если откат выполнялся, запись журнала удаляется — её наличие означает, что
  откат НЕ выполнялся, а файл трогал кто-то другой.

Сверка состояния: `POST /chat/rollback/preview` показывает, что сервер считает
последним применённым изменением, а sha256 файла на диске — что там на самом деле.

## Ограничение: ошибки рантайма в скриптах панели агенту не видны (2026-10-25)

<!-- LIMITATION -->
Ошибка вида

    ERROR: res://addons/godot_agent/agent_panel_part2.gd:640 - not all arguments
    converted during string formatting in operator '%'

возникает **внутри редактора** и до агента сама не доходит. Причины проверены,
а не предположены:

- `log_reader.collect_errors` читает `user://logs/godot.log` — лог ЗАПУСКА ИГРЫ.
  Скрипты панели (`agent_panel*.gd`) в игре не исполняются, поэтому их ошибок
  в этом файле нет;
- файла лога редактора не существует: после запуска редактора
  (`--headless --editor --quit`) каталог `%APPDATA%\Godot\logs` так и не
  появляется. Читать агенту физически нечего, пока редактор не запущен с
  `--log-file <путь>`;
- `gd_lint` ошибку не видит: синтаксис корректен, падение происходит в рантайме;
- headless-прогон её тоже не ловит: панель — editor-only UI, в `--headless`
  не исполняется.

Вывод: единственный надёжный канал для этого класса ошибок — детерминированная
статическая проверка. Она добавлена:
`python/tests/test_locale_format.py` (5 проверок) сверяет словари RU/EN и все
места `_t("ключ") % аргумент` во всех `.gd` аддона: число аргументов должно
совпадать с числом `%`-плейсхолдеров, ключ должен существовать, у ключа в RU и
EN должен быть одинаковый набор плейсхолдеров. Проверка ловит подмену: файл с
`_t("log_auto_ok") % [a, b]` даёт
`_ag_mut_test.gd:6 log_auto_ok — плейсхолдеров 1, аргументов 2`.

Второй, корневой фикс: словарь подключается через `preload("agent_locale.gd")`
(`agent_panel_part1.gd`, `agent_chat_view.gd`, `agent_start_screen.gd`).
Раньше путь вычислялся и грузился через `load()`; при сбое локали возвращался
`null`, `_t()` отдавала голый ключ (`log_auto_ok`), и первый же `%` на нём падал
именно этой ошибкой — в произвольной строке панели, пряча настоящую причину.
Теперь локаль не может быть `null`, а сломанный `agent_locale.gd` виден сразу и
по имени файла. Плата за это осознанная: битый словарь ломает загрузку панели
целиком (громко), вместо тихой деградации до ключей с падением в случайном месте.

Требование к стенду то же, что и выше: `.gd`-файлы компилируются при загрузке
редактора, поэтому после обновления панели редактор нужно **перезапустить**.
