### 3.1. Базис качества поиска (L2, харнесс, 15.10.2026)

Ручная проба «10 запросов глазами» (202 файла, @1 = 5/10, @3 = 7/10, @8 = 9/10)
заменена прибором: `python/tests/test_search_quality.py` + golden-set
`python/tests/data/search_golden_yandex_game_dev.json` (150 запросов, 7 ведёр;
эталон выведен из **исходников**, а не из индекса, — иначе прибор мерил бы сам
себя). Два среза по k = 8 (= `MAP_LIMIT`): `index` — ранжирование

`can_read_project_path` → `_rerank_hits[:8]`).

1. **P3 (`MAX_SYMBOLS = 60`) — не третий по важности, а первый.** Все **21

   `base_defender.gd`). Ни одного промаха вида «символ в индексе, но ранг
   низкий» — значит L5 (лимит) даёт больше, чем L3/L4, и стоит дешевле:
   порядок работ в §6 меняется на **L5 → L4 → L3**.
2. **`rare_func` и `rare_words` бьют в одну и ту же дыру.** 7 из 25

3. **P1/P2 видны, но их вклад меньше.** `intent`: hit@8 = 1.000 при mrr@8 =

   приоритет). `ambiguous` `sprite` в срезе `index` отдаёт `.tscn`-сцены
   раньше скриптов: счёт равный, решает алфавит (`scenes/` < `scripts/`) — это
   P2 в чистом виде; после L5 у `base_*.gd` появится `var:sprite`, но тай-брейк
   останется за алфавитом, пока не сделан L4.
4. **Слой MAP сам по себе не улучшает, а переставляет.** hit@8 совпадает
   (0.860 против 0.860), mrr@8 — в пределах шума; `ambiguous` в MAP даже ниже
   (0.933 → 0.811), а `rare_class` выше (0.920 → 1.000). Вывод: качество
   задаётся индексом (L3/L4/L5), `_rerank_hits` — только доводка. P4 (добор
   MAP до 8 слотов шумом) базисом не ловится вовсе: его критерий — не recall,
   а «завсегдатаи» в выдаче (L6).

Пороги-«храповик» (`THRESHOLDS` в харнессе) выставлены по измеренному базису
минус запас и снимать их нельзя: правка L3–L6, которая их ломает, — регрессия,

## 3.3. Результат L4: структурный тай-брейк вместо алфавита

Первопричина P2 в индексе: при **равном** score (`minilich/ml_project_index.py`,
`search()`) порядок задавался алфавитом пути — `scored.sort(key=lambda s:
(-s[0], s[1]["path"]))`. Строка решала судьбу восьмёрки: `enemy death` отдавал
первое место `base_enemy.gd` только потому, что `"base_" < "bomber_"`, а
`boss chest` — сцене `scenes/environment/boss_chest.tscn`, потому что
`"scenes/" < "scripts/"`. По замерам §3.4 алфавит определял 8 из 10 промахов
ведра `intent`.

Правка — не «умнее считать score», а честно развести равенство структурой:
`_TIE_BREAK = ("kind_rank", "phrase_name", "name_hits")`, путь остаётся
последним ключом как гарантия детерминизма. Признаки:

* `kind_rank` — код раньше сцены и ресурса. Сцена **применяет** структуру,
  скрипт её **объявляет**; это та же политика, что уже была в слое MAP
  (`_KIND_WEIGHT`, `_FRAG_KIND_RANK`), теперь она действует и в индексе.
* `phrase_name` — трёхзначный: 0 — запрос-фраза целиком совпал с именем
  объявления в коде (`act completed` → `func act_completed()`), 1 — такое имя
  есть только у сцены/ресурса, 2 — нет. Даёт словесному запросу узнать **своё**
  объявление, а не первое совпадение по одному слову.
* `name_hits` — сколько токенов запроса есть в имени **файла** (не в пути).
  Файл, названный по запросу, важнее файла, который его лишь упоминает.

Признаки **выбраны замером, а не вкусом**: перебрано 18 вариантов состава и
порядка (проба на 150 запросах, срез `index`). Плато 0.986 mrr@8 держат
`kind_rank, phrase_name, name_hits` и все их надмножества до
`kind_rank, phrase_name, exact_name, name_hits, path_hits, class_decl`, поэтому
`exact_name`, `path_hits` и `class_decl` **удалены** — измерения они не дают, а
карты в памяти стоят. Признак `shallow` (меньше вложенности — раньше) **навредил**
(0.982): он поднимал `scripts/main.gd` выше `scripts/autoload/map_manager.gd` на
`act completed`. Порядок `phrase_name` вперёд `kind_rank` даёт 0.979, а
`name_hits` вперёд `phrase_name` — 0.974.

Стоимость: поисковые карты (`phrase_post`, `name_post`, `kind_rank`) строятся
один раз на версию индекса и кэшируются вместе с постингами, **формат индекса не
изменён** — пересборка не нужна, время поиска не выросло.

Итог по срезу `index` (mrr@8): overall 0.907 → **0.986**, `intent` 0.625 →
**0.873**, `ambiguous` 0.933 → **1.000**, `rare_words` 0.837 → 1.000,
`rare_signal` 0.975 → 1.000, `rare_class` 0.920 → 1.000. Критерий L4 выполнен:
`bomber_enemy` больше не проигрывает `base_enemy` по алфавиту.

Тесты: `tests/test_search_quality.py`, класс `StructuralTieBreakTest` — четыре
свойства на синтетическом проекте: файл, названный по запросу, впереди соседа при
равном score; запрос-фраза находит своё объявление раньше файла со словом; скрипт
впереди своей сцены (только срез `index`); порядок детерминирован при двух
одинаковых вызовах. Плюс `tests/test_librarian.py::_search_bruteforce` —
эталон-перебор — повторяет новое правило порядка, и `test_search_matches_bruteforce`
держит совпадение индекса с перебором.

## 3.4. Результат L4b и полное сравнение шагов

Та же первопричина P2 жила **во втором месте** — в слое MAP:
`librarian._rerank_hits` заканчивался `rescored.sort(key=lambda x: (-x[0], x[1]))`,
то есть при равных весах снова побеждал алфавит пути, и `boss_chest.gd` уступал
своей же сцене. Правка в одну строку: `rescored.sort(key=lambda x: -x[0])` —
сортировка Python стабильна, поэтому равенство теперь разрешает **порядок
индекса**, а индекс с L4 разводит его структурно. Вес кандидата тай-брейк не
отменяет: он работает только внутри равенства.

Замер L4b (тот же полигон, тот же индекс, срез `map`): mrr@8 0.880 → **0.885**,
`intent` 0.686 → 0.693, `rare_words` 0.810 → 0.817, `rare_signal` 0.975 →
1.000; ни одно ведро не просело. Прирост скромный — вес в `_rerank_hits` и так
почти всегда разводит кандидатов; ценность в том, что **последнее слово больше
не за алфавитом**.

Тест: `MapRerankOrderTest` (два теста, проект не нужен) — при равных весах
порядок остаётся порядком индекса, а сильный кандидат всё равно обходит порядок.

## 3.7. Результат L6: слой MAP добивался шумом до восьми слотов

Индекс возвращает пул из 24 кандидатов (`MAP_LIMIT * _RERANK_POOL`), а MAP

## 4. Скрытый дефект: регрессия производительности до 127x



Замер **на одном и том же проекте, одним и тем же вызовом** — 0.8.0 (бэкап) против
0.8.11 (установка). Параметры одинаковы: `search_project_text(root, шаблон,
max_results=12, context_lines=0)`, лучшее из 3 прогонов.

| шаблон | 0.8.0 | 0.8.11 | раз | результат |
|---|---|---|---|---|
| `take_damage` | 21 мс | **2662 мс** | **×126.8** | идентичен, 12 строк |
| `artifact` | 49 мс | **2655 мс** | ×54.2 | идентичен, 12 строк |
| `save_game` | 76 мс | **2760 мс** | ×36.3 | идентичен, 12 строк |
| `enemy` | 1 мс | 16 мс | ×16.0 | идентичен, 12 строк |

Ответ **побайтно тот же** — это чистая регрессия скорости, а не поведения.

**Почему разброс в 100 раз и почему это важнее остальных пунктов.**
`search_project_text` прерывает обход сразу, как только одиночный шаблон набрал
квоту `max_results` (`project_tools.py`, строки 1023–1029: `truncated = True;
if all(c >= max_results for c in counts): return results, True`). Поэтому:

* **частый** шаблон (`enemy`) набирает 12 совпадений в первых же файлах и выходит
  досрочно — регрессия не видна (1 → 16 мс);
* **редкий** шаблон (имя конкретного символа — `take_damage`, `save_game`) квоту не
  набирает никогда, обход идёт **по всему дереву**, и платится полная цена (×127).

То есть регрессия бьёт ровно по рабочему сценарию агента «найди конкретный символ».
Это же объясняет, почему профиль Библиотекаря целиком состоит из одного вызова:

```text
ЗАПРОС 'take_damage'  ИТОГО 3173 мс
  обходов search_project_text: 1   суммарно 3124 мс  pattern='take_damage'
  по слоям: _fragments 3131 мс → _grep_token 3131 мс; _grep_patterns 0 мс ×2;
            _structure 2 мс; _autoloads 15 мс; _callers 0 мс; _signal_wiring 0 мс
ЗАПРОС 'enemy death'  ИТОГО 54 мс
  обходов: 1   суммарно 17 мс   pattern='enemy'      ← досрочный выход
ЗАПРОС 'artifact manager'  ИТОГО 2715 мс
  обходов: 1   суммарно 2680 мс  pattern='artifact'
```

**Механизм.** `_filter_project_scan_entries` вызывается на **каждый каталог** обхода
и для каждой записи зовёт `classify_project_path` → `_resolved_project_path` →
`os.path.realpath`, а поверх этого `can_read_project_path` классифицирует путь
**второй раз**. На Windows `realpath` — это `GetFinalPathNameByHandle`
(`_getfinalpathname`), то есть открытие handle на каждую запись: **43 844
системных вызова = 2.474 с** из 3.347 с профиля. В 0.8.0 была дешёвая проверка
`startswith` по относительному пути; `SEARCH_EXTS` в обеих версиях одинаков, так
что дело не в расширениях.

**Направление починки (решения политики обязаны остаться теми же).**

1. Не классифицировать запись дважды: `can_read_project_path` — это
   `_path_access_allowed(classify_project_path(...), ...)`, значит достаточно одной
   классификации и вызова `_path_access_allowed` напрямую (минус 2 `realpath` из 5
   на каждую запись каталога).
2. `realpath(project_root)` внутри одной операции обхода постоянен, а считается
   трижды на запись (`_scan_res_path` + дважды `_resolved_project_path`) — считать
   один раз на вызов.
3. Записи, физически совпадающие с родителем (не симлинк и не junction), не требуют
   `GetFinalPathNameByHandle`: канонический путь родителя уже известен из шага
   обхода, поэтому достаточно дешёвой проверки последнего компонента
   (`os.path.islink` / `os.path.isjunction` — Python 3.12+). Это снимает самый
   дорогой вызов на запись.
4. Каталоги, уже вырезанные `EXCLUDED_DIRS`, не должны доходить до проверки политики.

Критерий L8: редкий шаблон на полигоне **≤ 400 мс** (сейчас 2662 мс), при этом
`tests/test_access_policy_flow.py` зелёный и выдача побайтно та же.

### Результат L8 (14.10.2026, полигон)

## 5. Функция со связями вместо строк (требование владельца)

**Требование.** Агент должен уметь получать не просто найденные строки, а
**функцию со всеми её связями**: объявление, параметры, локальные переменные,
члены класса, которые она трогает, все места вызова по проекту, сигналы.

**Хорошая новость: данные уже есть, парсить заново не нужно.** Семантический
индекс (`godot_tools/gd_semantic_parser.py`) хранит:

- `declarations` с видами `class_name / class / function / signal / variable /
  constant / enum / **parameter**`; у локальных переменных `owner` = id функции;
- `references` — каждое употребление с `owner` и
  `context ∈ {identifier, member, call, type}`;
- `strings` — все литералы.

Ключевое: **лимит символов основного индекса (`MAX_SYMBOLS`, сейчас 400) не
касается семантического индекса** — там данные полные. Значит карточка символа
может быть точной там, где MAP урезан.

Прототип на полигоне для `take_damage` — один запрос, мгновенно:

```text
ОБЪЯВЛЕНИЯ (2):
  res://scripts/base/base_enemy.gd:1314  kind=function
     параметры: damage, damage_type, hit_data, is_dot, suppress_visuals
     локальные: accuracy (L1318), final_block (L1321), final_dodge (L1327), lifesteal (L1353)
     обращается к членам: current_hero, get, has_method, heal
  res://scripts/base/base_hero.gd:872  kind=function
     параметры: raw_damage, damage_type, attacker
     локальные: is_combat_damage, is_ranged, actual_damage
     обращается к членам: emit, has_mirror_aegis, is_armor_indestructible, ...

СВЯЗИ ПО ПРОЕКТУ (43 ссылки: call=2, member=41)   ФАЙЛОВ ЗАТРОНУТО: 20
```

Контраст: MAP не нашёл **ни одного** из этих двух объявлений, а карточка нашла
оба точно. Ещё один плюс: карточка **не даёт ложных срабатываний** — греп по
подстроке `take_damage` цепляет `take_damage_from_enemy`, семантический индекс — нет.

**Ограничение:** `start`/`end` в `declarations` — это границы **имени**, а не тела
функции. Для выдачи тела целиком нужен `gd_functions.extract_functions`.
